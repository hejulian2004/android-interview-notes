## 如何使用

1. **先讲项目，再背原理。** 每道题先尝试用 30–60 秒说清结论、项目中的做法和一个边界，再练深入追问。
2. **按证据回答。** SSH Mobile 的具体实现以代码为准；Compose FeedLine 主要依据原简历，未逐项审查其仓库；实习依据你的陈述，不虚构公司内部细节。
3. **参考答案不是个人经历证明。** 对没有亲自参与、没读懂或无法复现的实现，不直接照读“我设计了”。先明确你的真实参与范围、使用 AI 工具的方式，以及自己完成的设计、评审、调试和验证。
4. **回答到边界更可信。** “这里采用了什么机制”不等于“所有故障都已解决”。不把库提供的能力说成自研协议，也不把设计上限和测试阈值当性能实测。
5. **把待确认项补全。** 尤其是崩溃率统计口径、隐私问题修复与复测、真实设备上的性能数据、实习到岗安排。

### 事实标签

- **代码已核验**：有具体源码或 Git 变更支持；不代表本次重新运行过测试。
- **简历／本人确认**：来自你提供的材料或补充，需要你能展开真实操作细节。
- **通用原理／设计建议**：用于回答基础题或讨论改进，不表示项目已经实现。
- **待确认**：不能用肯定语气编出结果。可回答“目前实现到……，这一点尚未做专项验证”。

## 90 秒项目介绍参考

> SSH Mobile 是面向移动运维的跨平台客户端，包含 SSH 多终端、tmux 会话恢复、SFTP 文件管理、服务器监控、局域网传输和屏幕共享，并集成模型 API 辅助执行运维任务。
>
> 我会重点介绍三条技术主线：一是 Rust/Tokio 网络运行时与 Flutter 的跨语言集成，包括命令结果关联、超时和资源释放；二是 QUIC／Relay 文件传输中的断点恢复、完整性校验和接收完成确认；三是手机端 Agent 的工具调用编排、任务审批、执行前目标复核和预算控制。
>
> 性能方面，项目把非必要网络组件改为按需初始化，将耗时密钥计算放入工作 Isolate，SFTP 使用分块流式读写，并通过局部状态订阅减少无关重建。目前我能说明这些改动的代码与机制，但没有可复核的优化前后耗时或内存数据，因此不会给出未经确认的提升比例。

使用时将“项目实现”与“我实际负责”分别说清；这段是组织思路，不要求逐字背诵。

## 三条必须守住的口径

- **自研范围**：自研的是 SDK、运行时和业务集成；Rust、Tokio、QUIC、Protobuf 及密码算法本身不是你发明的。
- **性能范围**：移除“首帧后 900 ms 预热定时器”不等于启动缩短 900 ms；分块大小不等于总内存峰值；仓库测试用例存在不等于所有测试在所有设备上通过。
- **实习范围**：0.25% 是你确认的整体 SDK 指标，不是已证明由某次个人修复带来的降幅；隐私案例已确认发现风险，尚未确认具体整改与复测结果。

## 一、SSH Mobile：Rust SDK 与可靠网络传输


> 阅读方式：每题的“面试回答”可以作为约 30—60 秒的首轮答案；“追问”用于第二轮展开。“代码事实”表示仓库中已有对应实现；“设计原则”表示应该理解的技术知识，不等于你已实现或测试了全部方案。不要把代码存在说成性能已量化，不要把项目采用的开源协议说成个人发明。

<a id="q-n01"></a>
### N01. SSH Mobile 到底解决什么问题？核心竞争力是什么？

**面试回答：**它是面向移动端的远程服务器管理与协作工具，不只是一个 SSH 登录页面。基础功能包括多服务器连接、多窗口终端和 tmux 会话恢复，以及 SFTP 文件操作；进一步提供监控、局域网传输和手机端 Agent。我的项目介绍会重点放在跨平台 Rust 网络 SDK、可恢复文件传输和端侧工具执行上：它们涉及异步状态、跨语言生命周期和故障恢复，而不是简单堆界面。

**追问：**你的贡献和使用开源库有什么区别？
- 区分“协议库能力”和“项目工程设计”：Tokio 提供异步运行时，QUIC/密码学依赖成熟实现；项目价值在命令事件协议、状态与连接解耦、跨端桥接和恢复流程。
- 不应说“独立实现 QUIC 协议栈”“自研加密算法”，也不应把所有仓库贡献默认归于自己。面试前按提交核对个人负责范围。

**代码事实：**以下问题围绕当前简历的 SDK 与可靠传输描述展开，不把网络 SDK 的自定义传输和 SSH/SFTP 混为一条协议链路。

<a id="q-n02"></a>
### N02. 为什么用 Rust，而不是全部使用 Dart 或 Kotlin？

**面试回答：**主要目标是复用网络核心，而不是先假设 Rust 一定更快。连接管理、传输状态和协议处理集中在 Rust 后，Flutter 通过统一接口调用，避免各端维护不同逻辑。Rust 的类型系统有利于约束资源所有权，Tokio 适合组织大量等待 I/O 的任务。代价是构建、多架构打包、FFI 调试和资源生命周期更复杂，所以 UI 与交互状态仍留在 Flutter。

**追问：**怎样证明选择合理？
- 先看复用边界、协议一致性和维护成本，再测吞吐、CPU、内存、启动时间；没有同条件基线，不能说“比 Dart 快多少”。
- 小型纯平台业务未必值得引入 Rust；SDK 边界应稳定，避免每个细小 UI 动作都跨 FFI。

**代码事实：**项目确有 Rust/Tokio 核心和 C ABI 桥接；这是架构选择证据，不是语言性能胜出的实验结论。[FFI 实现](https://github.com/hejulian2004/ssh_mobile/blob/main/native/network_core/crates/network-ffi/src/lib.rs)

<a id="q-n03"></a>
### N03. 画一下从 Flutter 按钮到 Rust 再回到界面的调用链。

**面试回答：**可以画成“Flutter 业务层 → 命令编码 → C ABI → Rust 运行时 → 网络任务 → 原生事件队列 → 后台 Isolate 拉取并解码 → Dart 业务状态”。这里有两个返回层次：同步调用首先报告命令能否入队，真正的业务结果由后续事件报告。实时会话适配层通过 commandId 找回对应 Future，避免把入队成功当成执行成功。

**追问：**哪里最容易出错？
- 命令提交与 pending 注册的先后次序、事件在超时或 dispose 后到达、事件消费者停止后 native handle 被释放。
- 架构图必须标出谁拥有 handle、谁释放字节缓冲、谁拥有 pending 表，而不只画语言方框。

**代码事实：**入队/完成分离已核对到实时会话命令适配层，不应扩大为所有 SDK API 都使用相同关联机制。[实时适配层](https://github.com/hejulian2004/ssh_mobile/blob/main/apps/ssh_mobile_full/lib/app/realtime_feature_adapters.dart)

<a id="q-n04"></a>
### N04. Rust 的所有权、借用、生命周期分别解决什么问题？

**面试回答：**所有权回答谁负责资源释放，借用允许暂时使用资源而不转移所有权，生命周期约束引用不能比被引用对象活得更久。常见规则是在同一时刻允许多个共享引用，或者一个排他的可变引用。它们能在编译期排除很多悬垂引用和数据竞争，但不能自动解决死锁、协议重复执行，也不能自动保证 FFI 裸指针有效。

**追问：**`String` move 后为什么不能再用？`&str` 和 `String` 有什么不同？
- `String` 持有可增长字符串的所有权；`&str` 是字符串切片引用。move 是所有权转移，不等于一定深拷贝数据。
- 返回借用需要说明其对应输入/存储的生命周期；不能返回函数局部变量的引用。

**项目边界：**SDK 中强调资源生命周期是有意义的，但不能说“用了 Rust 就没有内存问题”，FFI 与 `unsafe` 仍需人工证明契约。

<a id="q-n05"></a>
### N05. `Send`、`Sync`、`Arc`、`Mutex` 和 `tokio::spawn` 怎么联系起来？

**面试回答：**`Send` 表示值的所有权可以安全跨线程转移，`Sync` 表示共享引用可以安全跨线程使用。`Arc` 解决线程安全引用计数，不代表内部数据自动可变或线程安全；共享可变状态通常还需要锁。Tokio 多线程任务可能在不同工作线程恢复，所以 `spawn` 要求 Future 满足相应的 `Send` 和 `'static` 约束，尤其要检查跨 `.await` 保存了哪些值。

**追问：**`'static` 是不是必须一直活到进程退出？
- 不是；这里主要是不依赖短寿命外部借用。任务可以很快结束并释放拥有的对象。
- `Rc<RefCell<T>>` 不能简单代替跨线程共享方案；也不要靠随意 `unsafe impl Send/Sync` 消除编译错误。

**原则来源：**[Rust Send/Sync](https://doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html)、[Tokio spawning](https://tokio.rs/tokio/tutorial/spawning)。面试中的类型解释不表示项目每处共享状态都采用同一种锁。

<a id="q-n06"></a>
### N06. `async/await` 等于开线程吗？Tokio 适合什么工作？

**面试回答：**不等于。异步函数生成 Future，运行时轮询它；等待网络就绪时任务让出执行机会，线程可以处理其他任务。它适合大量 I/O 等待，不会自动加速 CPU 密集计算。长时间同步计算或阻塞调用会占住运行时工作线程，需要分离到适当工作池，或者调整任务粒度。

**追问：**为什么用了 async 仍然卡 UI？
- Dart 的同步 FFI 调用或长计算仍可能占用当前 Isolate；给函数加 `async` 不能把同步工作自动搬到后台。
- Rust 的异步任务也必须主动到达可让出执行权的点，不能在循环里一直占 CPU。

**项目落点：**网络事件 poll 放后台 Isolate，密钥相关计算下沉 Isolate，是针对执行位置的处理；并非“所有函数加 await”就完成优化。[Dart 并发模型](https://dart.dev/language/concurrency)

<a id="q-n07"></a>
### N07. 锁应该怎么用？为什么不能随意持锁跨 `.await`？

**面试回答：**先缩小锁保护的数据和临界区，在锁内完成条件检查、状态修改或取出待处理对象，再释放锁做 I/O。跨 await 持锁可能让其他任务长期等待，甚至形成环路死锁。异步锁允许等待锁时不阻塞线程，但并不能解决锁顺序错误，也不是所有场景都比普通互斥锁更好。

**追问：**一定不能持锁 await 吗？
- 不是绝对禁止；确需串行保护异步资源时可以使用合适的异步锁，但要说明期间阻塞谁、取消后状态是否完整。
- 复杂连接状态可考虑单任务拥有状态，通过 channel 接收命令，减少共享锁；这是可选设计，不要冒充项目已全面 actor 化。

**项目落点：**丢唤醒修复的关键就是“锁内检查并建立观察关系，锁外等待”，详见 N16。

<a id="q-n08"></a>
### N08. 为什么用 C ABI？FFI 和 JNI、平台通道有什么区别？

**面试回答：**FFI 是跨语言调用机制，C ABI 是函数调用和数据布局的互操作约定。项目通过 C ABI 暴露 Rust SDK，Dart 可以直接调用原生库；JNI 是 Java/Kotlin 与 native 的桥梁，Flutter 平台通道更适合调用 Android/iOS 平台能力。它们不是互相替代所有场景的方案，我会按跨端网络核心与平台专属能力划分边界。

**追问：**为什么不直接传 Rust 的 `Vec` 或 `String` 给 Dart？
- Rust 内部对象布局、析构和所有权不能作为稳定的跨语言约定；桥接常使用显式指针、长度、状态码及配套释放函数。
- `extern "C"` 不等于自动内存安全；字符串编码、长度、整数位宽、线程约束都要约定。

**代码事实：**SDK 确实采用 C ABI，而不是把全部桥接说成 JNI。[FFI 入口](https://github.com/hejulian2004/ssh_mobile/blob/main/native/network_core/crates/network-ffi/src/lib.rs)

<a id="q-n09"></a>
### N09. FFI 最重要的资源与异常约束是什么？

**面试回答：**我会把接口当成所有权契约来检查：输入缓冲在调用期间是否有效，Rust 是否复制或保留它；输出由谁分配、由谁释放；handle 在哪些线程可用，什么时候禁止再调用。异常方面，不应让 Rust panic 以未约定方式跨过 C 边界；需要把失败变成可识别的返回或事件，并区分参数错误、运行时关闭和业务失败。

**追问：**如何发现 use-after-free、double-free？
- 给 handle 明确 running/stopping/disposed 状态，集中释放路径；检查关闭与 poll 并发，做重复 dispose 和关闭中调用测试。
- `catch_unwind` 不是任意崩溃的保险：它不能修复未定义行为，也不能承诺捕获 abort。

**边界：**这是审计清单，不能未经逐项检查就说所有原生入口都有 panic 隔离或已经通过内存检测工具。

<a id="q-n10"></a>
### N10. Protobuf 的作用是什么？为什么不是 JSON？

**面试回答：**Protobuf 提供结构化 schema 和紧凑二进制消息，适合在 Dart/Rust 间统一命令和事件类型，也减少大量手写字段转换。JSON 的可读性更好，调试和临时接口也方便，所以不是绝对优劣。选择 Protobuf 后仍需要处理协议版本、未知字段和错误信息，不能因为有 schema 就忽略兼容性。

**追问：**Protobuf 是否自动解决 TCP 粘包？
- 不解决。消息编码和传输分帧是不同层；字节流上还要有长度前缀或其他边界协议。FFI 中的指针+长度也必须校验。
- 不能随意复用已删除字段编号；新增字段和默认值可能改变业务语义。大消息应限制长度，防止恶意分配。

**代码事实：**项目用 Protobuf 桥接命令/事件；协议知识参考 [Protobuf encoding](https://protobuf.dev/programming-guides/encoding/)。不宣称它实现了零拷贝。

<a id="q-n11"></a>
### N11. Dart Isolate 和线程有什么区别？为什么把 poll 放进去？

**面试回答：**Isolate 有独立的 Dart 状态和事件循环，通常通过消息通信，而不是共享普通可变 Dart 对象。把阻塞式原生 poll 放到工作 Isolate，可以避免占用 UI Isolate 的事件循环。它解决的是执行位置隔离，但 native 内存不因此自动安全；如果多个 Isolate 使用同一个原生 handle，仍需遵守 native 的并发和生命周期协议。

**追问：**把数据发给 Isolate 有没有代价？
- 有序列化、复制或可转移对象管理的成本，应限制消息大小和频率；逐字节事件可能得不偿失。
- Isolate 并不保证后台任务在 Android 进程被杀后继续运行；系统生命周期是另一层问题。

**代码事实：**[NetworkNativeIsolate](https://github.com/hejulian2004/ssh_mobile/blob/main/packages/infrastructure/ssh_mobile_network_native/lib/src/network_native_isolate.dart) 承担事件拉取。一般模型见 [Dart 官方文档](https://dart.dev/language/concurrency)。

<a id="q-n12"></a>
### N12. 为什么选择“poll 事件”，不直接从 Rust 回调 Dart？

**面试回答：**poll 可以把事件消费入口集中在 Dart 工作 Isolate，便于明确线程、批量读取和退出顺序。回调也可以实现，但要额外考虑回调调用线程、Dart 运行时约束以及对象已经释放时的回调。poll 的代价是需要设计等待和唤醒机制，不能用高频空循环；消费速度不足时也要有队列控制。

**追问：**poll 是不是一定轮询耗电？
- 不一定。阻塞等待事件与不断空转查询是两回事；真正的耗电取决于等待机制、超时频率和唤醒次数。
- 需要测空闲 CPU、唤醒频率和事件延迟，不能从函数名推断性能。

**代码事实：**项目使用工作 Isolate 拉取原生事件；这里的方案比较不表示已完成回调版与 poll 版的对照实验。

<a id="q-n13"></a>
### N13. 命令返回成功为什么不等于业务完成？commandId 有什么作用？

**面试回答：**跨语言异步链路至少有“已接收/入队”和“执行完成”两种状态。比如命令进入队列后，网络连接仍可能失败。如果 UI 收到入队成功就展示已完成，会产生错误状态。实时会话适配层用 commandId 把最终结果事件与 pending Future 关联，最终成功或失败由结果事件决定，而不是 queueStatus。

**追问：**结果很快回来怎么办？重复结果怎么办？
- 审计 pending 是否在结果可能到达前建立；若提交失败要回滚 pending。
- 完成操作应只发生一次，迟到或重复事件不能再次完成同一个 Future，也不能误匹配后续命令。

**代码事实：**当前实时适配层包含 pending 上限 32 和 30 秒超时；它们是实现配置，不是并发性能上限或普适最优值。[实现](https://github.com/hejulian2004/ssh_mobile/blob/main/apps/ssh_mobile_full/lib/app/realtime_feature_adapters.dart)

<a id="q-n14"></a>
### N14. 超时、取消、dispose 分别是什么意思？

**面试回答：**超时表示调用方在期限内没有得到结果，不等于底层没有执行。取消是尝试停止操作，需要协议或任务显式支持。dispose 是对象结束服务并释放资源，应停止接收新命令，结束 pending 等待，终止事件消费，然后按依赖顺序释放 native 资源。三者如果混为一谈，容易出现“界面显示失败但远端已经执行”或释放后仍有事件访问对象。

**追问：**超时后能直接重试吗？
- 对查询通常比较容易，对创建、写入或执行操作必须考虑幂等标识、查询最终状态或重复执行风险。
- Rust Future 被 drop 不表示已发送的远端副作用回滚；阻塞任务也未必随等待方退出立即结束。

**代码事实：**实时适配层会清理 pending；原生桥接强调先结束 poll Isolate 再销毁 handle。不要把本地取消描述成分布式事务回滚。

<a id="q-n15"></a>
### N15. 有界队列和背压解决什么？容量设成 64 就安全了吗？

**面试回答：**当生产事件比消费更快时，无界队列会持续占内存。有界队列限制积压，并要求明确队列满时等待、拒绝、合并或丢弃的策略。传输进度可以考虑合并为最新状态，但完成和错误不能随意丢。容量 64 只是当前进度通道的配置，还需要结合单条消息大小、并发传输数和消费者速度评估整体内存。

**追问：**背压会不会导致死锁？
- 会：如果生产者持有消费者所需的锁，再等待队列空间，可能形成互相等待。
- 队列满时如果把最终 ACK 或关闭消息卡在普通进度之后，也会造成业务停滞；应评估控制消息与数据/进度的优先级。

**代码事实：**传输进度 channel 是有界设计；不能据此声称全系统内存恒定或所有事件队列策略完全相同。[transfer.rs](https://github.com/hejulian2004/ssh_mobile/blob/main/native/network_core/crates/network-core/src/transfer.rs)

<a id="q-n16"></a>
### N16. 讲一个最能体现并发理解的实际问题：丢唤醒怎么产生、怎么修？

**面试回答：**仓库有一次背压等待的丢唤醒修复。关键场景是任务检查到暂时不能继续，准备等待；如果状态在“检查”和“建立等待”之间变化，通知又没被当前等待逻辑可靠观察，就可能一直睡眠。修复改用带 generation 的 `watch` 状态观察，并把条件检查和订阅放到同一锁保护下，释放锁后等待，再循环检查条件。重点不是替换 API 名字，而是关闭检查与订阅之间的竞态窗口。

**追问：**`Notify` 不是会存 permit 吗？为什么还能错？
- `notify_one` 的 permit 语义不等于任意广播和多等待者场景都安全；具体要看 `notify_waiters`、订阅时机与检查顺序。不能说“Notify 天生丢消息”。
- `watch` 只保留最新值，适合观察状态版本变化，不适合必须逐条消费的业务事件；被唤醒后必须重新检查真实条件。
- 验证应覆盖更新发生在检查前、订阅附近、等待后，以及多个等待者和关闭场景；不要仅靠 sleep 的偶然调度。

**代码事实：**[修复提交 1182e60](https://github.com/hejulian2004/ssh_mobile/commit/1182e60b9c84eaf6f1def404dc3e5c62b4c29f6b)。原理参考 [Notify](https://docs.rs/tokio/latest/tokio/sync/struct.Notify.html)、[watch](https://docs.rs/tokio/latest/tokio/sync/watch/index.html)。提交可证明修复存在，不证明你本人以某种方式首次定位它。

<a id="q-n17"></a>
### N17. SSH 如何保证连接安全？密码和主机指纹分别验证谁？

**面试回答：**SSH 建立加密连接，同时需要区分服务器身份验证和用户身份验证。服务器主机密钥用于确认连接的是预期机器，密码或用户私钥用于证明用户身份。如果为了方便忽略主机密钥变化，即使通道加密，也可能把密码或命令交给错误的服务器。首次连接需要明确的信任建立方式，后续变化应提示或阻止，而不是静默接受。

**追问：**TOFU、私钥口令分别是什么？
- TOFU 是首次使用时建立信任，并记录后续比较的身份；首次信任本身仍有风险。
- 私钥口令保护本地私钥文件，不等于登录密码；密钥保存、日志脱敏和平台安全存储是另外的工程问题。

**项目边界：**SSH 是核心功能；这里是应掌握的安全原理，不把未逐行核对的主机指纹 UI 或密钥存储方案写成已完成事实。

<a id="q-n18"></a>
### N18. 多窗口终端、SSH channel 和 tmux 会话恢复是什么关系？

**面试回答：**界面上的窗口、SSH 连接、连接中的 channel 和远端 tmux session 是不同概念。SSH 断线后普通交互会话可能结束，而 tmux 让终端会话由远端服务端进程管理；客户端重新连接后可以 attach 回去。项目的 tmux 恢复重点是恢复远端工作上下文，不等于恢复原 TCP 连接，也不等于网络中断期间所有 UI 字节都自动补齐。

**追问：**怎样处理 resize、退出和多窗口切换？
- 终端尺寸要同步到远端 PTY；窗口关闭、detach 和 kill session 语义不同。
- 多窗口应隔离输出订阅和生命周期，避免关闭一个窗口误关共享连接；具体是否共享底层连接必须按代码说明。

**项目边界：**简历可说“多窗口与 tmux 会话恢复”，不要直接推导为“所有服务器上的任务永不丢失”。

<a id="q-n19"></a>
### N19. SFTP 和 FTP、FTPS、SCP 有什么区别？如何做大文件传输？

**面试回答：**SFTP 是运行在 SSH 上的文件传输协议，不是给 FTP 简单加密；FTPS 则是 FTP 结合 TLS。对大文件，关键是避免先把整个文件读进内存，而是分块读写、等待下游写入并处理取消和错误。项目有从选择文件时预读全部内容改为流式访问的提交，因此我会强调减少整文件加载，而不编造峰值内存降低比例。

传统 SCP 协议与 SFTP 是不同协议；还要区分协议名和 `scp` 命令：OpenSSH 9.0 起，`scp` 默认使用 SFTP，`-O` 才选择传统 SCP，所以不能仅凭命令名判断底层协议。[OpenSSH scp 手册](https://man.openbsd.org/scp)

**追问：**分块越大越快吗？
- 大块减少调用次数，但增大内存与取消延迟；小块相反。吞吐还受窗口、RTT、服务端和磁盘影响。
- 历史实现中的 256 KiB 是块大小，不是整个任务的峰值内存；并发任务和协议缓冲仍占空间。

**代码事实：**[SFTP 流式优化提交](https://github.com/hejulian2004/ssh_mobile/commit/df2cc184a8fd5eb2edf876bd59c2c57e0ad1c356)。不要把 SFTP 的块传输和自研网络 SDK 的断点协议混为一套实现。

<a id="q-n20"></a>
### N20. QUIC 为什么基于 UDP 还能可靠？它与 TCP 的核心区别是什么？

**面试回答：**UDP 提供数据报，QUIC 在其上实现连接、可靠流、确认、重传、流控和拥塞控制，因此“基于 UDP”不意味着“不可靠”。QUIC 支持多条流，某条流丢包一般不必让其他流等待同一字节序列补齐；但同一条流仍有顺序交付约束，多个流也可能共享拥塞控制资源。项目采用 QUIC 直连，但是否更快要看实际网络和实现测量。

**追问：**QUIC 是否完全没有队头阻塞？
- 不能这么说；它减少 TCP 多路复用场景下的跨流传输层阻塞，不消除单流顺序依赖和应用层依赖。
- UDP 被限制、弱网络和 CPU 开销都可能影响表现；QUIC 并非必然优于 TCP。

**原理来源：**[RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)。项目使用成熟 QUIC 实现，不是自行实现可靠 UDP 协议栈。

<a id="q-n21"></a>
### N21. QUIC、TLS、TCP、WebSocket、Relay 分别在哪一层？

**面试回答：**TCP 和 QUIC 是传输层方案，QUIC 集成 TLS 握手来建立安全保护；WebSocket 提供面向消息的双向应用通信，常运行在 TCP/TLS 之上。Relay 是拓扑角色，即让中间节点转发流量，它可以承载在 WebSocket 等通道上。因而“QUIC 对 Relay”不是同一层的协议比较，准确说法是优先 QUIC 直连，不可用时使用符合策略的中继路径。

**追问：**既然中继有 TLS，为什么还需要端到端加密？
- TLS 到中继通常只保护客户端与中继这一跳；中继如果终止 TLS，是否能看到业务明文取决于是否还有端到端加密层。
- 不把 TLS 1.3 在 QUIC 中的集成描述为“在 UDP 上直接套完整 TCP/TLS 字节流”。

**原理来源：**[RFC 9001](https://www.rfc-editor.org/rfc/rfc9001.html)。项目路径说明应以当前配置和代码为准，不承诺所有回退都一定可用。

<a id="q-n22"></a>
### N22. 什么是 NAT？为什么不能保证所有设备都能直连？

**面试回答：**NAT 在内外网地址和端口之间建立映射，入站流量能否到达还受映射方式、防火墙和网络策略影响。设备发现不等于公网可达；同一 Wi-Fi 也可能存在客户端隔离。项目因此需要直连和 Relay 两类路径，直连失败时选择受认证与加密策略约束的中继，而不是一直阻塞业务等待理想网络。

**追问：**是否实现了 STUN、TURN、ICE 或 UDP 打洞？
- 这些是相关概念，但除非找到对应实现与测试，不应因为“有直连/中继”就宣称完整实现 ICE 或所有 NAT 穿透。
- 需要区分发现、地址候选、可达性检查、认证、路径建立和业务恢复，每一层都可能失败。

**项目边界：**可说支持 QUIC 直连与 Relay，不说“任意网络秒连”或“百分之百穿透”。

<a id="q-n23"></a>
### N23. 为什么把 TransferIdentity 和 ConnectionSession 分开？PathLease 是什么？

**面试回答：**文件传输是一个业务任务，网络连接只是某次承载它的路径。若任务直接拥有某个连接，断线后业务状态容易一起丢失。项目用 TransferIdentity 标识 peer 与 transfer，把进度等业务状态保留下来；每次尝试通过 PathLease 获取当前可用路径。旧连接失效后，新尝试重新借用路径并恢复，而不是让已经失效的连接对象长期留在业务层。

**追问：**这是不是无缝迁移或 QUIC 自带迁移？
- 不是同一个概念。这里是业务重试与路径解耦，可能建立新的会话并重新握手；QUIC 的网络路径迁移是协议层能力。
- “lease”体现限定使用关系，不表示连接永久有效；操作仍必须处理租用后路径失效。

**代码事实：**[transfer.rs](https://github.com/hejulian2004/ssh_mobile/blob/main/native/network_core/crates/network-core/src/transfer.rs)。正确表述是“支持中断恢复”，而非“切换无感、零丢包”。

<a id="q-n24"></a>
### N24. 断点续传是否就是保存 offset 后继续写？

**面试回答：**offset 是必要信息，但还需要确认续传的是同一个文件和同一个任务，接收端已有内容可信，发送与接收对续传位置一致。项目接收端使用 `.part` 临时文件恢复偏移，完成后做整文件 SHA-256 校验。发生不匹配时应显式失败或按策略重新传输，不能只看到文件长度相等就认定内容正确。

**追问：**源文件在传输中变化、临时文件被改动怎么办？
- 需要文件身份与摘要等信息参与判断；完整摘要可以发现最终内容不一致，但不能让中间错误自动消失。
- offset 应以接收端已接受的数据状态为依据；发送端“已发字节”不代表接收端已经持久保存。

**代码事实：**[receiver.rs](https://github.com/hejulian2004/ssh_mobile/blob/main/native/network_core/crates/network-transfer/src/receiver.rs)。不要说“任意文件修改后仍能无缝续传”。

<a id="q-n25"></a>
### N25. 为什么还要 SHA-256？传输协议不是已经保证可靠了吗？

**面试回答：**传输层可靠性主要解决传输中的顺序和丢失；业务层还需要确认最终文件与预期内容一致，尤其涉及续传、文件选择和磁盘内容。SHA-256 用于整文件完整性校验。但没有可信来源的摘要只能做一致性比较，不能单独证明发送者身份；身份和真实性还要依赖认证通道、MAC 或签名等机制。

**追问：**为什么不只用文件大小或 MD5？
- 相同大小不代表相同内容；安全要求下不能把弱摘要当作抵抗恶意碰撞的充分保障。
- 哈希可以分块读取并增量计算，无需把整个文件放内存；是否采用某种并行计算优化需要看实际实现。

**代码事实：**项目有 SHA-256 整文件校验，不据此声称“端到端绝不会损坏”或“摘要等于加密”。

<a id="q-n26"></a>
### N26. 为什么需要接收端完成 ACK？ACK 丢了怎么办？

**面试回答：**发送端写完流只说明本地把数据交给了链路，不能代表接收端已完成校验和最终提交。项目在接收端完成校验、flush 与重命名后发送完成确认。如果文件已经完成而 ACK 丢失，发送端会面临结果不确定，因此接收端需要识别已完成任务，在重试时返回一致的完成状态，而不是重复创建或破坏文件。

**追问：**这是 exactly-once 吗？
- 更准确是通过稳定任务身份、状态识别和幂等处理减少重复副作用。ACK 丢失、进程崩溃和状态持久化边界仍要分析，不能笼统宣称全局 exactly-once。
- 需要检查重复请求是否确实对应同一内容，不能仅按文件名误判“已完成”。

**代码事实：**[接收提交流程](https://github.com/hejulian2004/ssh_mobile/blob/main/native/network_core/crates/network-core/src/transfer_operations/incoming.rs)、[完成文件识别](https://github.com/hejulian2004/ssh_mobile/blob/main/native/network_core/crates/network-transfer/src/receiver.rs)。

<a id="q-n27"></a>
### N27. `.part`、flush、rename 是否保证断电不丢文件？

**面试回答：**临时文件让未完成内容与正式文件区分，校验成功后再重命名可以减少用户看到半成品的机会。但 flush 通常不等于数据已经可靠落到物理介质，rename 的原子性也受文件系统、路径和操作方式影响。断电持久性还可能涉及文件同步、目录同步及错误处理，因此项目当前的提交顺序不能直接包装成断电零丢失保证。

**追问：**进度 100% 后 UI 该显示什么？
- 可以区分“字节传输完成”“正在校验”“正在提交”“已完成确认”；不要把进度字节达到总大小当成业务完成。
- 校验、重命名失败时仍是失败状态，应该保留可诊断原因并按策略清理或保留临时文件。

**代码事实：**代码有校验后 flush/rename/ACK；本题特别限定持久性承诺，不补造 fsync 已实现的事实。

<a id="q-n28"></a>
### N28. 幂等、重试、超时如何一起设计？

**面试回答：**首先给业务操作稳定身份，再明确每一步的可重试范围。对于传输，重试应继续同一任务并重新取得可用路径，接收端依据状态决定续传或返回完成。超时只是结果未知，不能一律新建任务；否则可能重复写入。重试还应受次数、总时长与取消状态控制，避免网络故障时无限消耗资源。

**追问：**指数退避解决所有重试问题吗？
- 它缓解请求密度，不解决重复副作用、身份碰撞和错误分类。鉴权失败、协议不兼容等通常不是盲目重试能解决的。
- 多设备同时重试可加入抖动；这是设计建议，未核对具体配置前不要说项目已完整实现。

**项目落点：**TransferIdentity、PathLease、完成状态识别分别解决“是哪次业务”“走哪条路”“是否已经做完”，不能只用一个连接 ID 代替全部语义。

<a id="q-n29"></a>
### N29. Noise XX 是什么？你“自研”的是密码学吗？

**面试回答：**不是。Noise 是握手协议框架，XX 是其中一种交互握手模式，用于双方交换信息并派生安全会话密钥。项目通过 `snow` 等成熟实现组织握手，而不是自行实现底层密码学。真正需要自己负责的是把握手身份与预期设备绑定、正确管理会话生命周期，并确保路由切换时不静默降级安全策略。

**追问：**用了 Noise XX 就自动防中间人了吗？
- 不能省略身份信任。握手获得的远端静态公钥仍要与预期身份、既有信任或带外验证相联系，否则“对端有某把钥匙”不等于“对端就是目标设备”。
- 前向安全、重放保护和身份隐藏要结合具体模式、密钥保存与会话管理分析，不能只背算法名。

**补充范围：**Noise/AES-GCM 属于项目安全深挖，不是当前精简简历必须主动展开的首轮卖点。[项目握手](https://github.com/hejulian2004/ssh_mobile/blob/main/native/network_core/crates/network-core/src/crypto_handshake/noise.rs)、[Noise 规范](https://noiseprotocol.org/noise.html)。

<a id="q-n30"></a>
### N30. AES-GCM、nonce、epoch、方向和计数器是什么关系？

**面试回答：**AES-GCM 属于认证加密，不只加密内容，也用于检查密文及关联数据是否被篡改。最重要的使用约束之一是同一密钥下不能重复 nonce。项目中 nonce 组织涉及 epoch、方向和计数器：方向区分双向消息，计数器区分同一方向消息，epoch 帮助划分密钥/会话阶段。关键是从重连、重启、并发发送和计数器溢出角度证明不会复用组合。

**追问：**换一个连接 ID 就一定安全了吗？
- 不一定，要看实际密钥与 nonce 如何派生；旧密钥继续用且计数器重置就可能危险。
- 解密认证失败应拒绝消息，不能忽略错误继续处理；密钥轮换还要处理双方状态不同步。

**代码事实：**[crypto/context.rs](https://github.com/hejulian2004/ssh_mobile/blob/main/native/network_core/crates/network-core/src/crypto/context.rs)。可以介绍设计约束，不把阅读实现说成已完成独立密码学审计。

<a id="q-n31"></a>
### N31. Relay 能看到什么？端到端加密还留下哪些风险？

**面试回答：**如果业务在两端完成加解密，Relay 转发的是密文，就不需要让中继掌握业务明文。但它仍可能观察连接时间、流量大小、设备间通信关系，也可能丢弃或延迟数据。端到端加密不解决终端被攻破、密钥泄露、流量分析和拒绝服务，所以安全描述应明确威胁模型，而不是简单说“绝对安全”。

**追问：**直连失败能不能临时关闭加密走中继？
- 不能把可用性回退变成静默安全降级。路径选择应服从安全策略；身份验证失败不应被当成普通网络故障绕过。
- 项目存在不同 E2EE 策略时，要说明哪些模式允许哪类路由，不要把开发调试模式说成生产默认策略。

**项目边界：**“Relay 转发密文”是设计属性，“中继看不到任何信息”则不成立；也没有足够证据承诺系统已获得安全认证。

<a id="q-n32"></a>
### N32. 如果面试官说“你这套网络看起来很复杂，为什么不直接 HTTP 上传”？

**面试回答：**如果需求只是把文件交给固定服务器，HTTP 上传或对象存储确实更简单。项目同时涉及设备间直连、多种路径、持续会话和恢复，因此需要统一的网络抽象。但复杂性必须有边界：协议实现交给成熟库，业务只关心操作身份、进度、结果与取消，不应该感知所有底层路由细节。设计价值不是组件越多越好，而是把故障复杂度限制在 SDK 内。

**追问：**哪些地方可以继续简化？
- 减少相似状态机的重复实现，集中错误分类和关闭流程，明确哪些恢复由业务负责、哪些由连接层负责。
- 应通过日志和测试证明复杂性确实换来可维护的行为；不能只凭抽象名字证明架构优秀。

**项目落点：**用 TransferIdentity/PathLease 这一个清晰例子回答，优于罗列所有 manager、supervisor 和 session 类名。

<a id="q-n33"></a>
### N33. 你如何验证可靠传输和并发生命周期？

**面试回答：**我会按状态转换设计故障矩阵，而不是只测成功上传。关键节点包括申请接收、首块写入、传输中、校验中、重命名前后及 ACK 发出后，分别注入断线、重复请求、取消和进程退出。再检查任务状态、临时文件、最终文件、摘要、pending 表及 native handle 是否一致。跨语言关闭还要覆盖 poll 正在等待时 dispose 和结果超时后迟到。

**追问：**怎么区分你做过和你计划做？
- 可以展示仓库已有测试与修复；涉及真实弱网、不同设备或长时间压力测试时，只有实际运行记录才能说验证通过。

- 指标建议：成功率、恢复耗时、重复提交次数、队列长度、峰值内存、事件延迟；它们是补测方向，不是现有成果数字。

**代码证据入口：**[性能回归报告](https://github.com/hejulian2004/ssh_mobile/blob/main/docs/reports/PERFORMANCE_REGRESSION_REPORT.md)、[故障矩阵](https://github.com/hejulian2004/ssh_mobile/blob/main/docs/NETWORK_FAULT_MATRIX.md)。回答时使用“已有覆盖 / 尚待补测”两列。

### N34. 选一个项目问题，用 STAR 做两分钟深挖。

**建议主题：背压等待中的丢唤醒，而不是“把语言换成 Rust 提升性能”。**

**S｜背景：**网络流需要在背压条件下等待可发送状态，多个异步任务会同时观察和改变状态。仓库出现过等待方错过状态变化、无法继续推进的并发问题。

**T｜目标：**让“检查不可继续 → 等待变化 → 再检查”的过程不存在竞态窗口，同时避免持锁等待阻塞状态更新者。

**A｜行动（以代码事实为底稿）：**围绕条件检查和通知订阅的时序分析，使用 generation 与 `watch` 保留可观察的状态变化；把条件检查和订阅放在同一锁内，释放锁后等待，恢复后重新检查条件。提交还处理了重复打开流时不应误关闭原有流的问题。若本人确实参与定位，可补充自己的日志和复现方法；否则不要冒充亲历定位全过程。

**R｜结果：**代码层面修正了相应等待与重复请求处理逻辑，明确了状态同步不变量。没有量化压测资料时，就说“修复了该竞态路径并补齐相应验证”，其中“补齐验证”也须以实际测试提交和运行结果为准；不说“吞吐提升 50%”“彻底解决所有死锁”。

**面试官追问的关键句：**
1. 为什么换成 `watch`？因为观察的是状态版本，不需要逐条消息；最终正确性仍由锁内检查/订阅和循环复检保证。
2. 为什么不加 sleep？sleep 只改变触发概率，不证明时序正确。
3. 为什么不一直持锁？更新方可能也需要这把锁，等待方会阻止条件变成可继续。
4. 怎么设计测试？控制“观察状态—注册等待—状态改变—唤醒”的交错顺序，覆盖多等待者、关闭与重复请求。
5. 你个人做了什么？只回答自己能结合提交、日志或调试记录证明的部分。

**备选主题：可靠传输的结果不确定性。**用“接收端已提交但 ACK 丢失”这个失败场景，串起任务身份、路径切换、续传、校验、完成确认与幂等，比逐个解释术语更能展示系统思考。

### N35. Linux/Windows 监控的 CPU、内存、网络、磁盘指标怎么算？

**面试回答：**监控不是只把命令输出画成图，首先要统一指标口径。CPU 使用率通常需要两个采样点计算累计运行时间的差值；网络速率通常是累计收发字节差除以实际时间差。内存要区分已用、可用与缓存，磁盘要区分容量占用和 I/O 吞吐。Linux 与 Windows 的数据来源和语义不同，应在采集层适配，给展示层提供注明单位和时间戳的统一模型。

**追问：**为什么算出的网络速度为负或 CPU 超过 100%？
- 计数器重置、接口变化、采样时间异常可能导致负增量，不能直接展示成负速度。
- CPU 需要说明是整机归一化还是按核累加；不同口径直接比较会误导。采样失败应标记缺失，不应伪造为零负载。
- UI 刷新频率、远端采样频率和历史数据长度分开控制；历史缓存要有容量限制。

**证据边界：**简历确认有 Linux/Windows 监控；此处是通用实现原则。尚未逐项核对实际命令、Windows API 和统计公式，面试前应打开对应采集器确认，不要直接背成“我用了某个系统命令”。

### N36. 屏幕共享完整链路是什么？WebRTC 与信令、媒体流的关系是什么？

**面试回答：**共享链路可以拆成屏幕采集、编码、会话协商、媒体传输、解码和渲染。WebRTC 是实时音视频与数据通信相关技术，不等于只用 WebSocket 发送截图。建立连接前还需要交换会话描述和网络候选，这个信令通道由应用组织；信令建立成功不代表媒体已经可达。ICE 用于候选连接检查，STUN/TURN 是常见相关机制，但实际项目是否采用完整链路必须看实现。

**追问：**你的 QUIC 网络 SDK 和 WebRTC 是不是同一套东西？
- 不能因为都有实时通信就混为一谈；要分别指出会话控制、信令和媒体分别由哪层承载。
- Relay 是泛称，不代表项目自研 Relay 就是标准 TURN 服务器；WebRTC DataChannel 也不能简单等同 QUIC stream。

**证据边界：**屏幕共享是项目功能；本题 WebRTC 是面试补充知识，不作为当前实际媒体传输栈的核实结论。只有找到具体依赖和媒体实现后，才回答项目用了何种编码与传输。[WebRTC 官方规范](https://www.w3.org/TR/webrtc/)

<a id="q-n37"></a>
### N37. 屏幕共享怎么控制延迟？为什么不能直接照搬文件传输策略？

**面试回答：**文件传输主要追求完整正确，而实时画面还强调时效性。网络拥塞时如果无限缓存旧帧，最终可能画面完整但已经延迟数秒；因此需要结合编码器与传输层控制码率、分辨率、帧率和队列长度。并不是所有帧都能随意丢弃，帧间依赖和关键帧恢复也要考虑。优化时要拆分采集、编码、排队、网络、解码和显示的耗时，不能只测 RTT。

**追问：**关闭共享和隐私方面要注意什么？
- 用户停止后要真正停止采集和媒体发送，清理 track/编码器/会话等资源；UI 显示停止而后台继续采集是严重问题。
- 采集权限、敏感内容提示及系统中断处理取决于平台，不能把浏览器 `getDisplayMedia` 当成 Android 原生实现。

**证据边界：**这是设计与验证框架，不宣称项目已实现动态码率、自适应帧率或测得特定端到端延迟。浏览器采集规范只用于理解采集与传输分层：[Screen Capture 工作草案](https://www.w3.org/TR/screen-capture/)。

## 二、SSH Mobile：Agent、性能优化与架构


> 阅读标记：**项目事实**来自当前代码或可定位的历史提交；**设计追问**是技术原理或建议方案，不代表项目全部实现。口述答案可用第一人称，但只有自己确实参与的工作才能说“我实现”。本章不声称端侧大模型推理，也不虚构耗时、帧率、内存降幅。

<a id="q-g01"></a>
### G01｜你的手机端 Agent 是什么？和聊天机器人有什么区别？

**30–60 秒回答：** 我做的是运行在客户端的 Agent 编排，不是把大模型部署到手机上。模型推理由配置的模型 API 完成，客户端负责组织上下文、消费流式回复、处理工具调用，并通过已有 SSH/SFTP 等能力操作用户选定的服务器。与普通问答相比，关键区别是形成“请求模型—检查工具调用—获得必要批准—执行工具—回传结果—继续推理”的闭环，同时有计划、执行范围和预算约束。我的工程重点是让模型建议能够可控地转化为操作，而不是宣称训练了一个模型。

**追问：** 断网后还能运行吗？终端/SFTP 能否独立使用？
- 模型 API 不可达会影响 Agent 推理，不等于已有 SSH 功能必然不可用；还取决于目标服务器网络。
- 对已有结果可展示历史；不要把“本地保存历史”说成“离线推理”。

**边界/易错：** “手机端 Agent”说明编排与工具入口在客户端；不意味着所有计算、远端命令执行都发生在手机。

<a id="q-g02"></a>
### G02｜Agent Loop 的状态流转与退出条件如何设计？

**30–60 秒回答：** 一轮先准备上下文和本轮可用工具，再调用模型。若只有文本且无后续工具请求，就结束；若有工具调用，先校验名称、参数、目标与审批，再执行并把结构化结果关联回对应调用，进入下一轮。不能只依赖模型主动结束，还要处理用户取消、网络失败、工具失败、调用预算以及循环上限。当前 `llm_stream_handler.dart` 组织这个过程，并将工具循环交给控制器处理；模型输出只是请求，不是已经执行成功的事实。

**追问：** 多个工具能否并行？工具失败是否全部重试？
- 独立只读任务才适合并发；有顺序依赖或副作用的任务需要显式排序。
- 超时可能是“已执行但响应丢失”，不能无条件重试写操作。应先核对外部状态，必要时让用户判断。

**边界/易错：** 不把“循环有限制”夸大成“任何任务都不会失控”；限额之外还需要执行端校验。

<a id="q-g03"></a>
### G03｜SSE 是什么？为什么不能对每个网络数据块直接 jsonDecode？

**30–60 秒回答：** SSE 是基于 HTTP 的事件流格式，常用来逐步返回模型输出。网络分块与业务事件不是同一个边界：一个事件可能拆成多个块，一个块也可能包含多个事件，UTF-8 字符还可能跨块。正确思路是先增量解码字节，再缓冲并按 SSE 事件规则解析，最后对完整的业务 payload 做 JSON 解析，而不是每收到一块就 jsonDecode。项目有流式模型调用，但面试时还要对应具体 provider 的适配器解释格式，不能把一种供应商的结束标记当作 SSE 通用标准。

**追问：** `data:` 多行怎么办？`[DONE]` 是协议标准吗？
- 标准 SSE 的多条 `data:` 行需要按规则合并，空行形成事件边界；注释/心跳也要能跳过。
- `[DONE]` 是某些模型接口的约定，不是 SSE 的统一结束机制。

**边界/易错：** 上面是协议正确性要求，不能在未检查对应适配器测试前声称所有分片情况已覆盖。参考 [HTML SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

<a id="q-g04"></a>
### G04｜流式 Tool Calling 的参数为何要累积？怎样避免执行半截 JSON？

**30–60 秒回答：** 工具名、调用 ID、参数可能分多次返回，参数甚至只是一个尚未闭合的 JSON 字符串片段。因此要按该 provider 提供的调用索引或 ID 汇聚属于同一次调用的增量，等调用完成后再解析和做 schema/业务校验。文本输出和工具调用要分开处理，不能因为屏幕上出现一段类似命令的文本就执行它。项目工具循环接收归一化的调用结果；具体分片字段由模型协议适配层处理。

**追问：** 两个工具参数交错、流中途断开怎么办？
- 维护每个调用独立的累积状态；无法解析或没有可靠完成信号的调用不执行。
- 对断流给出“不完整/失败”状态，而不是自行补齐参数猜测用户意图。

**边界/易错：** 对不同供应商，增量可能是追加片段，也可能是结构化更新；不能机械地对所有字段拼接字符串。属于需结合适配器逐项核对的细节。

<a id="q-g05"></a>
### G05｜为什么先生成计划，再执行？批准计划等于批准所有操作吗？

**30–60 秒回答：** 运维任务可能跨多个步骤，先把目标和待办步骤展示出来，可以让用户在实际改动前确认范围。项目区分计划模式和执行模式，部分工具只能在相应状态暴露。但批准高层计划不应自动变成对一切命令的永久授权，具体操作仍要经过目标、参数和风险检查。尤其远程写入、上传、重命名、删除等，应遵循实际工具审批规则，而不是模型说“已获准”就直接执行。

**追问：** 模型执行中改计划怎么办？
- 新增目标、扩大范围或增加高风险动作，应重新检查并按需要重新批准。
- 计划完成要以真实工具结果与必要的回读为依据，不能只修改 UI 上的勾选状态。

**边界/易错：** “可审批计划”不是完整事务，也不保证失败后自动回滚。

<a id="q-g06"></a>
### G06｜审批目标快照解决了什么问题？执行前为什么再检查一次？

**30–60 秒回答：** 典型问题是用户批准时选的是服务器 A，等待期间切成 B；如果执行时重新读取当前选择，已批准操作可能落到错误对象上。项目把审批请求与目标上下文绑定，在 `executeApproved` 中先调用 `isApprovalTargetCurrent`，目标变更返回 `approval_target_changed`；执行路径还会检查显式连接 ID 是否在允许范围内。这是在降低“检查时与使用时状态不一致”的风险，不只是在界面上弹一个确认框。

**追问：** 这能解决所有 TOCTOU 问题吗？
- 不能。客户端目标选择一致，不代表远端文件内容、符号链接、权限或进程在审批后没有变化。
- 对远端条件敏感的动作，需要额外的版本/哈希/前置条件校验；这是进一步设计方向，不能冒称现有全部覆盖。

**证据：** [ai_tool_service.dart](https://github.com/hejulian2004/ssh_mobile/blob/main/packages/features/feature_ai/lib/src/tools/ai_tool_service.dart)。

<a id="q-g07"></a>
### G07｜动态工具路由怎么做？为什么不能把它当安全沙箱？

**30–60 秒回答：** 当前 `ToolExposureRouter` 根据请求需要的能力、计划状态、是否有已批准计划、WebView 会话及工具白名单等筛选提供给模型的工具，同时记录选择和阻断原因。这样可以减少无关工具和上下文负担，也降低误选概率。但这是“模型能看见哪些工具”，不等于工具执行的最终授权。服务器相关请求即使没有预选连接也可能仍暴露相关工具，所以最终必须在执行端检查目标和审批，不能只靠路由过滤。

**追问：** 关键词路由会漏召回吗？
- 会。当前能力识别包含关键词规则，表达歧义可能造成漏选/误选。
- 应通过可解释日志和典型请求测试改进，而不是声称具备完美语义理解；兜底也不能绕过执行权限。

**证据：** [tool_exposure_router.dart](https://github.com/hejulian2004/ssh_mobile/blob/main/packages/features/feature_ai/lib/src/tools/tool_exposure_router.dart)。

<a id="q-g08"></a>
### G08｜工具预算、循环上限、Token 限额分别控制什么？

**30–60 秒回答：** 工具预算限制实际工具调用，防止反复试错带来资源或操作风险；循环上限限制 Agent 推理—执行轮次；上下文 Token 限额约束每次模型输入容量与成本。三者不能混用：一次回复可以请求多个工具，而一次循环也可能不产生工具。当前流处理器使用 `LlmToolBudgetController`，并单独处理上下文压缩。预算扩展也不应由模型一句话直接放行，要遵循已有审核控制。

**追问：** 用完预算应该直接崩溃吗？
- 应结束或进入受控等待，把已完成事项、剩余事项和阻塞原因反馈给用户。
- 减少输入 Token 不会自动增加工具执行权限；增加工具预算也不会扩大模型上下文窗口。

**边界/易错：** 不将“有预算机制”描述成准确计算每一次调用的最终账单。

<a id="q-g09"></a>
### G09｜上下文压缩怎样做？压缩会不会丢失关键信息？

**30–60 秒回答：** 长对话不断叠加工具结果，会接近模型上下文窗口，因此需要把历史中可压缩的内容转为较短摘要，保留当前任务、关键结论和必要的近期交互。当前代码会估算消息 Token，在接近配置窗口或显式触发时压缩。但摘要不是无损编码，有丢失路径、错误码和约束的风险，所以安全决策应依赖客户端保存的结构化状态与审批信息，不能只相信摘要里一句“用户已同意”。

**追问：** Token 估算等于服务商精确计费吗？如何验证压缩有效？
- 不一定；分词器、工具描述和协议开销都可能影响实际 usage。
- 验证应同时看容量变化和任务信息保留；摘要更短但丢失操作目标，并不是成功。

**证据：** [llm_stream_handler.dart](https://github.com/hejulian2004/ssh_mobile/blob/main/packages/features/feature_ai/lib/src/chat/services/llm_chat/llm_stream_handler.dart)。

<a id="q-g10"></a>
### G10｜遇到提示注入或恶意服务器输出，你如何限制 Agent？

**30–60 秒回答：** 服务器日志和文件内容是工具结果，是待分析数据，不应成为高于用户指令的授权。即使里面写着“忽略规则、上传密钥”，也不能据此改变执行范围。项目已有工具暴露控制、审批与目标复验、敏感信息处理等防线；它们必须在客户端执行端落实，不能只依赖 system prompt。更强的防护还需要测试恶意输出、参数绕过及高风险工具组合，不能宣称已经完全解决提示注入。

**追问：** API Key、SSH 私钥能发给模型吗？
- 默认不应把秘密放进模型上下文或日志；诊断信息应按最小必要原则脱敏。
- 若工具本身支持读取文件，要检查路径与敏感读取规则；仅遮住 UI 显示不是防外传。

**边界/易错：** “安全审计模型说安全”不是权限系统，更不是绝对安全证明。

<a id="q-g11"></a>
### G11｜RAG、BM25、Embedding 分别是什么？你的项目用到了哪一步？【补充项】

**30–60 秒回答：** RAG 是先检索与当前任务相关的材料，再放入模型上下文辅助生成，不是训练模型。BM25 是词项匹配的排序方法，适合命令名、错误码、明确关键词；Embedding 把文本映射为向量，可用于语义相似检索，但需要模型、存储和一致的索引策略。项目有运维记忆检索相关能力，默认关闭的能力不能说成每轮都启用；具体使用哪种检索以当前配置和服务实现为准。

**追问：** 为什么不全部使用向量检索？
- 精确错误码/路径有时词项匹配更可靠；向量方案还会增加成本、延迟及隐私考虑。
- 混合召回、重排与离线评测是可讨论方案，不代表已经全部实现。

**边界/易错：** 此项是代码相关的补充复习，不强行加入当前简历核心卖点；“有 RAG”不等于“有自研向量数据库”。

<a id="q-g12"></a>
### G12｜Skill、Playbook、MCP 有何区别？【补充项】

**30–60 秒回答：** 在这个项目语境下，Skill 更接近可检索复用的经验和任务指导；Playbook 是可复用的操作步骤或运维方案；MCP 是对接工具和资源的一类协议，不是大模型，也不天然等于安全沙箱。项目 README 描述的本地 MCP 服务是桌面端能力，不能说 Android 手机同时运行了同样的服务。面试可把它们作为扩展设计解释，但不需要为了显得技术栈多而全部塞进主叙事。

**追问：** 工具一旦通过 MCP 暴露，就不用审批了吗？
- 不对。协议只负责交互约定；身份、授权、参数校验及审批仍由实现负责。
- 当前项目区分不同信任策略，但硬性安全检查不应被“可信 Agent”标签绕开。

**边界/易错：** 不将“接入某协议”说成“自研该协议”，也不把桌面能力冒充移动端已交付能力。

<a id="q-p01"></a>
### P01｜挑一项性能优化，用 STAR 讲清楚：冷启动。

**30–60 秒回答：** **S/T：** 应用启动并不立即需要全部网络和传输能力，我要减少非必要初始化占用启动关键路径。**A：** 先保留轻量启动壳，把非首屏必要的网络身份和 Runtime 改为首次使用时初始化；并发首次调用复用同一个初始化任务；密钥派生和证书生成移到工作 Isolate，快传接收端等到首次进入相关功能再激活。**R：** 提交与回归用例能证明冷状态不提前创建相关资源、并发共享初始化以及失败后可重试。我没有保留可信的前后耗时记录，因此只描述减少启动阶段工作量，不报虚构的毫秒或百分比。

**追问：** 懒加载是否只是把卡顿转移到首次点击？
- 是存在这个代价，所以还要观察首次功能可用耗时，给加载/错误/重试状态；有数据后才决定哪些组件适合适量预热。

**证据：** [冷启动优化提交 53e5cd1](https://github.com/hejulian2004/ssh_mobile/commit/53e5cd15b3747025f013d0bf40d17c182fb530d6)。

<a id="q-p02"></a>
### P02｜你怎么定义冷启动耗时？第一帧出现就是启动完成吗？

**30–60 秒回答：** 必须先约定起止点。冷启动指进程不在运行的启动场景；第一帧只说明画面开始呈现，不一定代表首页可交互或核心数据准备完成。我会分别记录进程/启动入口到第一帧、到首页可交互，以及首次进入 SSH/快传到功能 ready 的时间。懒加载可能改善第一帧，却增加首次功能等待，所以需要一起看，不能只挑最好看的一个指标。

**追问：** 怎么控制实验变量？
- 固定真机、构建模式、版本、账户/数据量、网络和缓存条件；多次重复，报告中位数和尾部数据。
- 网络依赖可拆为本地可控场景与真实网络场景；先定义口径再比较。

**边界/易错：** 删除一个“首帧后等待 900ms 的预热定时器”不等于冷启动减少 900ms。

<a id="q-p03"></a>
### P03｜什么是 Single-flight 初始化？为什么加一个 bool 不够？

**30–60 秒回答：** Single-flight 是同一资源首次被多个调用方同时请求时，大家等待同一个进行中的 Future，而不是各建一份连接、密钥或原生句柄。单独一个 initialized 布尔值只能表示完成与否，表达不了“正在初始化”；而先检查再创建也可能在异步切换中重复创建。合理实现会保存正在进行的 Future，成功缓存资源，失败清理进行中状态以允许重试，同时明确销毁后是否允许再次初始化。

**追问：** 失败 Future 一直缓存会怎样？初始化中 dispose 怎么办？
- 失败 Future 永久保留会让所有重试重复得到旧失败。
- 初始化完成时要防止把资源发布给已销毁 owner；应及时清理或拒绝交付。测试包括同时首次调用、失败重试、初始化中退出。

**项目证据：** [STARTUP_INITIALIZATION.md](https://github.com/hejulian2004/ssh_mobile/blob/main/docs/STARTUP_INITIALIZATION.md) 与冷启动提交包含相关初始化/释放约束；具体方法签名以代码为准。

<a id="q-p04"></a>
### P04｜为什么把密钥派生放进 Isolate？async/await 不能避免卡顿吗？

**30–60 秒回答：** async/await 解决异步等待，不会自动把后续 CPU 计算换到其他执行单元。密钥派生、证书生成或大段解码若持续占用 UI Isolate，仍会妨碍响应与绘制。工作 Isolate 可以把合适的 CPU 工作移出去，但有启动、消息传递和资源成本。网络等待本身通常已经是异步 I/O，没有理由仅因为“是网络任务”就为每次请求创建 Isolate；应先确认阻塞点。

**追问：** 是否所有对象都能跨 Isolate 传递？每个包开一个 Isolate 合适吗？
- 要遵守可发送对象规则，原生句柄/控制器的归属也需明确；避免把 UI 对象和生命周期混过去。
- 高频小任务可以考虑长生命周期 worker，是否值得要靠测量，不是 Isolate 越多越快。

**参考：** [Dart Isolates 官方文档](https://dart.dev/language/isolates)。不要把 Dart Isolate 简化成共享内存的普通线程。

<a id="q-p05"></a>
### P05｜聊天输入卡顿，你具体改了什么？

**30–60 秒回答：** **S/T：** 输入是高频操作，如果每次 onChanged 都在聊天页面顶层 setState，可能连消息列表等无关区域一起重新 build。**A：** 历史提交把输入区提取为 `_ChatComposer`，用局部 `ValueNotifier` 管输入相关状态，并通过 Selector 订阅附件变化，减少顶层状态更新影响面。**R：** 代码层面缩小了更新范围；提交记录描述修复输入卡顿，但没有可靠 FPS 或重建次数对照，所以不会编造“提升多少倍”。

**追问：** build 多就一定卡吗？
- 不一定。要结合每次 build 的成本，以及 layout、paint、raster 等阶段；便宜的 build 不必为了数字少而过度优化。
- 优先让高频状态与其消费 UI 靠近，而不是全局禁止 setState。

**证据：** [输入区优化提交 606559b](https://github.com/hejulian2004/ssh_mobile/commit/606559b5d33a3a9afd07f10f97c331412973bdca)。

<a id="q-p06"></a>
### P06｜ValueNotifier、ChangeNotifier、Provider、Selector 分别负责什么？

**30–60 秒回答：** ValueNotifier 适合一个较小的可观察值；ChangeNotifier 适合对象管理多个关联状态并通知监听者；Provider 负责把实例提供给 widget 子树，不等于业务模型本身；Selector 从提供的状态中选出 UI 真正关心的值，减少无关通知造成的重建。项目不是把这些名称堆在一起，而是用全局注入管理共享服务、用页面 ViewModel 管业务、用输入区局部状态承接高频变化。

**追问：** Selector 返回原地修改的 List 有什么风险？
- 同一可变对象可能让比较判断失真，订阅端看不到期望的变化；应使用明确版本或稳定不可变快照等方式。
- notifyListeners 不等于每个像素立即重绘，不能把通知、build、paint 混为一谈。

**边界/易错：** API 比较策略要按依赖版本解释；不要背“Selector 一定使用某一种比较”而不看项目锁定版本。

<a id="q-p07"></a>
### P07｜监控图表为什么做缓存？缓存怎样保持正确？

**30–60 秒回答：** 图表随监控采样频繁更新，如果每次 build 都重复过滤列表、降采样、构造所有点对象，会增加无谓计算和分配。历史提交移除上层宽泛的 `context.watch`，更精确地订阅采样变化，并缓存降采样后的 `FlSpot` 和过滤结果。缓存必须用真正影响输出的条件失效，例如采样版本、时间窗口、筛选条件；否则虽然快了，却可能显示过期监控值。

**追问：** 降采样会丢峰值吗？
- 可能，因此算法应与用途匹配；若用于故障排查，不能只追求平滑而隐藏短时峰值。
- 具体是否保峰值要核对当前算法，不冒称采用了某个高级降采样算法。

**证据：** [监控订阅与缓存提交 833256a](https://github.com/hejulian2004/ssh_mobile/commit/833256ab73134d474daea8aa9790678976f9c70b)。

<a id="q-p08"></a>
### P08｜SFTP 大文件上传为什么改成流式？await 一次写入意味着什么？

**30–60 秒回答：** **S/T：** 选择文件时直接读完整 bytes，会让大文件大小影响内存占用。**A：** 历史提交把 FilePicker 改为不预加载文件数据，使用 `RandomAccessFile` 分块读取，再等待对应写入，配合进度、取消和异常清理。**R：** 避免业务层先把整份文件加载到内存；但实际峰值还包含协议缓冲、加密缓冲、队列和运行时开销，所以不能说一个 256KiB 块就代表峰值只有 256KiB。

**追问：** await write 就一定有端到端背压吗？
- 不一定，要看写入 Future 表示已消费、已入队还是已发送；下游内部无限排队仍会积累内存。
- 真正要检查整条链路的队列上限、读取速度和消费者完成语义。

**证据：** [流式文件上传提交 df2cc18](https://github.com/hejulian2004/ssh_mobile/commit/df2cc184a8fd5eb2edf876bd59c2c57e0ad1c356)。256KiB 是该历史实现参数，不是通用最优值。

<a id="q-p09"></a>
### P09｜终端大量输出为什么要批量更新？会不会丢内容？

**30–60 秒回答：** 终端输入速度可能远高于屏幕刷新频率，逐块立即触发 UI 和滚动会增加高频工作。历史提交使用自适应批量消费、节流和合并滚动，把多次更新归并处理。需要区分可覆盖的“进度类状态”和不可随意丢失的“终端字节数据”；队列处理和旧会话输出清理不能混成“随便丢日志”。过载策略还应明确是延迟、限量历史还是截断，向用户保持可解释。

**追问：** 25ms 节流是不是保证 40FPS？
- 不是，它只是调度配置；实际帧率还受工作量、设备、屏幕刷新率和渲染管线影响。
- 历史阈值也不一定是严格内存硬上限，单个超大 chunk 需要单独检查。

**证据：** [自适应批量提交 accae80](https://github.com/hejulian2004/ssh_mobile/commit/accae809a68a76f986bcf4033b6878aeea4f03d6)。

<a id="q-p10"></a>
### P10｜RepaintBoundary 为什么不是“加上就快”？Key 使用不当有什么问题？

**30–60 秒回答：** RepaintBoundary 用来隔离部分重绘，并不是阻止 widget build，也不是所有场景都更省。边界过多可能增加图层和内存成本。项目历史修复去掉了随字体/主题变化的动态 RepaintBoundary Key，避免把本可更新的子树错误当作新的身份而重建相关状态，同时清理过期会话待处理输出。核心不是记住一个控件，而是理解对象身份、状态保留和渲染边界的不同责任。

**追问：** 什么情况下 Key 应改变？
- 当确实需要表达不同业务身份并重置/迁移状态时；不要仅把显示属性变化编码成新身份。
- 是否有性能收益仍需对比 Timeline、重绘范围和内存，而不是只凭层数判断。

**证据：** [终端状态/边界修复 e739f87](https://github.com/hejulian2004/ssh_mobile/commit/e739f872404935d30d5886c226c625c240ee4cac)。

<a id="q-p11"></a>
### P11｜你如何证明这些优化有效？自动化测试通过够不够？

**30–60 秒回答：** 不够。功能测试能证明状态与行为符合预期，例如没有提前建资源、初始化只发生一次、取消后能释放；它不直接证明启动更快或内存更低。我会在固定真机与数据集上使用 profile 定位耗时，再用一致构建条件做前后对照，观察首帧/可交互、UI/raster 帧耗时、峰值 RSS/堆和吞吐。debug 带有额外开销，不适合作为最终性能结论。当前仓库有本地回归烟测，但缺少完整跨设备生产基线，所以要坦诚这一限制。

**追问：** 没有数据还可以写“优化”吗？
- 可以写具体结构改进与减少的工作，例如“非必要组件按需初始化”“避免整文件预加载”。
- 不应写“启动降低 60%”“零卡顿”“全量测试通过”；后续补测也要区分重现历史版本和当前版本。

**证据：** [性能回归报告](https://github.com/hejulian2004/ssh_mobile/blob/main/docs/reports/PERFORMANCE_REGRESSION_REPORT.md)。验收场景里的 10 万行、5 分钟等只是测试条件，不是已达成成绩。参考 [Flutter 性能实践](https://docs.flutter.dev/perf/best-practices)。

<a id="q-e01"></a>
### E01｜项目如何分层？为什么不是所有逻辑都写在页面里？

**30–60 秒回答：** 项目按 feature-first 组织功能模块，核心契约和基础设施分离，应用入口负责组合实例。页面主要负责布局和短生命周期的交互状态，ViewModel 负责业务校验和异步编排，底层基础设施封装 SSH/网络/持久化能力。这样 UI 不需要直接知道 Rust Runtime 或数据库如何创建，测试可以替换契约背后的实现，模块之间也不必互相访问内部字段。但分层只是控制变化，不是文件夹越多越高级。

**追问：** 怎么避免“上帝 ViewModel”？
- 把可独立复用的会话、工具执行、存储操作放入明确服务；ViewModel 只协调当前页面用例。
- 边界必须体现在依赖方向和资源归属上，而不只是目录名称。

**项目定位：** `packages/features`、`packages/core/app_core`、基础设施包及应用组合根；具体类名与当前分支核对。

<a id="q-e02"></a>
### E02｜AppRuntime、Provider 和页面的资源生命周期如何区分？

**30–60 秒回答：** AppRuntime 是应用级资源的所有者，组合根创建并通过根 Provider 注入共享服务；页面和路由持有的是借用关系，不能因为页面退出就销毁整个网络 Runtime。路由自己的 ViewModel、订阅和局部控制器则应在对应生命周期结束时释放。释放要处理进行中的异步任务和迟到回调，避免页面销毁后还更新 UI，或者已退出页面仍保留监听而泄漏。

**追问：** 单例就一定不会泄漏吗？页面 dispose 就能取消远端任务吗？
- 单例可能让不该常驻的对象长期可达；应用级常驻需要有意设计。
- 本地取消监听不等于取消底层 I/O，更不等于撤销已在远端执行的命令；各层要区分停止展示、停止等待和实际取消。

**边界/易错：** 不宣称语言有垃圾回收就无需释放原生句柄、文件、订阅或连接。

<a id="q-e03"></a>

## 三、Compose FeedLine 与 Android 基础


> **证据边界**：本章的 FeedLine 功能与架构依据原简历描述，未逐行核验项目源码。标为「原简历」的内容可作为复述基础，但具体类名、配置和测试结果仍应对照代码；标为「原理/改进」的是面试知识与可行方案，不等于项目已经实现。Room、AIDL、RecyclerView 等技能不要移植成 FeedLine 的实现。

> **优先级**：P0 必须能脱稿解释并画流程；P1 高频追问；P2 扩展准备。下面的「参考回答」是组织思路，不建议逐字背诵。

### 一、FeedLine 的项目主线与架构

<a id="q-c01"></a>
### C01｜P0：用一分钟介绍 Compose FeedLine，最能体现什么能力？
**参考回答（原简历）**：这是 Kotlin + Jetpack Compose 实现的动态信息流项目，覆盖文字、单图、多图和视频展示，以及发布、点赞、评论、删除、通知、刷新和媒体预览。我的重点不是堆页面，而是把用户操作、页面状态、网络与本地缓存串成可维护的数据流：界面发出 Intent，ViewModel 更新 State，Repository 协调 Retrofit 与 SQLiteOpenHelper 缓存，瞬时反馈通过 Effect 表达。列表侧使用稳定 key、不可变状态更新与 Coil 加载图片。

**追问**：你负责哪个部分？最难的问题是什么？回答时选一个自己确实调试过的链路，讲清触发条件、原因、修改和验证；没有真实性能数字就不报提升比例。

**易错点**：不能把「用了 Compose」当作性能证明；不能把普通缓存回退说成完整离线优先同步系统。

<a id="q-c02"></a>
### C02｜P0：画出一次下拉刷新从手势到界面的完整链路。
**参考回答**：UI 发出刷新意图，ViewModel 维护刷新中状态并调用业务入口；Repository 请求远端，成功时转换数据并按项目策略落盘，失败时尝试读取本地缓存，最后把结果映射成新的 UiState，UI 根据状态渲染。提示由 Effect 或可消费的提示状态表达。原简历明确有网络失败本地回退与 IO 持久化，但具体先落盘还是先显示、缓存过期策略需以代码为准。

**追问**：连续刷新如何避免旧响应覆盖新响应？可取消旧 Job、串行处理或校验请求序号；要说明取消是否能传到实际请求。

**易错点**：不要在 Composable 函数体直接请求网络；不要把刷新失败简单处理成清空已有列表。

<a id="q-c03"></a>
### C03｜P0：Intent、State、Effect 各放什么？
**参考回答（原简历 + 原理）**：Intent 表示用户或系统输入，例如 Refresh、Like(id)；State 表示当前可重建界面的事实，如列表、加载状态、错误状态；Effect 表示 Snackbar、滚动等一次性 UI 行为。这里的 Intent 是架构中的动作模型，不一定是 Android 的 `android.content.Intent`。页面业务状态以 State 为准，Effect 不应是判断「发布成功」的唯一证据。

**追问**：点赞成功属于 State 还是 Effect？点赞状态与计数是 State，成功提示可以是 Effect；二者不应相互替代。

**易错点**：不是所有点击都必须定义一个复杂 Intent 类；关键是状态归属清楚、修改路径可追踪。

<a id="q-c04"></a>
### C04｜P0：你这是 MVI 还是 MVVM？两者冲突吗？
**参考回答**：ViewModel 是状态持有者，因此可以说采用 MVVM 的组件组织，同时借鉴 MVI 的 Intent/State/Effect 与单向数据流。MVVM 更强调 View 与 ViewModel 的职责分离；MVI 风格强调输入集中处理、状态驱动界面。仅有几个命名为 Intent 的类，不足以证明实现了严格的 reducer、事件溯源或时间旅行调试。

**追问**：单向数据流的代价？状态建模与模板代码增多，大状态对象要控制更新粒度，异步事件仍需要明确并发策略。

**易错点**：不要说 MVVM 必然双向绑定、MVI 必然单线程；这是设计实践而非互斥标签。

<a id="q-c05"></a>
### C05｜P0：data/domain/presentation、Repository、UseCase 分别负责什么？
**参考回答（原简历）**：presentation 负责界面、ViewModel 和 UI 状态；domain 表达业务规则与业务操作；data 负责远端、本地与实体转换。Repository 向上提供一致的数据入口，隐藏 Retrofit 和数据库细节；UseCase 表达可复用的业务动作，避免 ViewModel 堆积业务判断。具体依赖方向应保证业务不直接依赖 Compose 界面。

**追问**：只有一次简单读取也要加 UseCase 吗？不必机械分层。规则复杂、跨 Repository 或需要复用时收益更明显。

**易错点**：包名分成三层不等于依赖已经解耦；也不要声称每个 UseCase 都经过充分单测，除非能展示。

<a id="q-c06"></a>
### C06｜P1：AnalyticsTracker 为什么单独抽象？
**参考回答（原简历 + 原理）**：原简历有 AnalyticsTracker。它的价值是把埋点接口与具体统计实现分离，业务调用只描述事件，不关心上传 SDK。测试时可替换成记录调用的 fake，检查点击或发布流程是否记录预期事件。实际哪些点已经接入、是否上传，需要看项目实现。

**追问**：Compose 重组会不会重复埋点？会有这种风险。点击事件适合在回调处理，曝光要定义可见性、去重范围和生命周期，不能直接写在可重组函数体内。

**易错点**：不能把「接口抽象」说成「完整数据分析平台」；埋点不能随意记录设备标识、令牌或用户正文。

### 二、Compose：状态、列表与媒体

<a id="q-c07"></a>
### C07｜P0：什么是重组？重组等于整页重绘吗？
**参考回答（原理）**：Compose 在观察到相关状态变化后，重新执行需要更新的可组合范围，以得到新的 UI 描述；它不等于每次把整页重新布局、绘制。组合、布局、绘制是不同阶段。Composable 应能安全重复执行，不应依赖执行次数产生业务副作用。状态读取的位置会影响需要更新的范围。

**追问**：怎么判断问题真是重组？结合重组观察、系统跟踪与帧耗时，区分组合开销、布局、图片解码、IO 和主线程阻塞。

**易错点**：重组次数少不一定更流畅；重组本身是正常机制，不应以完全消除为目标。

<a id="q-c08"></a>
### C08｜P0：什么是状态提升？FeedLine 的状态应该放哪里？
**参考回答（原理）**：将多个组件共享的状态放到能覆盖这些消费者的合适拥有者，通过 value 向下传、事件向上传。动态列表和业务加载状态适合由 ViewModel 持有；只影响单个组件、无需业务共享的展开状态可留在 UI。状态提升的目标是单一事实来源和可测试性，而非把所有 UI 细节塞进 ViewModel。

**追问**：视频预览的临时展开状态也需要数据库持久化吗？通常不需要，应按用户是否期待恢复来决定。

**易错点**：父子各保存一份点赞状态会造成不同步。参考：[Compose 状态指南](https://developer.android.com/develop/ui/compose/state)。

<a id="q-c09"></a>
### C09｜P0：remember、rememberSaveable、ViewModel 如何选？
**参考回答（原理）**：remember 在对应组合位置仍存在时保留值，不能独自应对 Activity 重建。rememberSaveable 可借助保存状态机制恢复支持保存的轻量 UI 数据，自定义类型可能需要 Saver。ViewModel 适合页面业务状态并可跨配置变更，但进程被杀后对象仍会消失。大列表、图片和业务记录应由持久化数据源恢复，而不是塞进保存状态。

**追问**：进程恢复怎么办？保存恢复业务所需的轻量参数，例如草稿 ID、筛选项；ViewModel 可通过 SavedStateHandle 读取，再重建数据。

**易错点**：不要说 ViewModel 永不销毁，或 rememberSaveable 等价数据库。参考：[Compose 状态指南](https://developer.android.com/develop/ui/compose/state)。

<a id="q-c10"></a>
### C10｜P0：为什么 LazyColumn 要 stable key？能保证不重组吗？
**参考回答（原简历 + 原理）**：原简历写了稳定 key。列表头部插入、删除或移动时，key 帮助框架识别「仍是同一条动态」，让相关 UI 状态与元素身份匹配。应优先使用唯一且稳定的业务 ID，而不是会变化的位置下标。key 解决身份问题，不保证每个 item 都不重组，状态变化和参数变化仍可能触发更新。

**追问**：重复 key、临时发布 ID 替换为服务器 ID 怎么办？要明确稳定身份策略，避免重复和无意重建；这属于需核验的实现细节。

**易错点**：不要把 key 当成缓存所有列表项的机制。参考：[Lazy 列表指南](https://developer.android.com/develop/ui/compose/lists)。

<a id="q-c11"></a>
### C11｜P0：为什么强调不可变更新？`List` 就一定不可变吗？
**参考回答**：对点赞动态创建新的对象与列表快照，有助于让状态变化可追踪，避免原地修改使旧状态同时变化。Kotlin 的 `List` 是只读接口，不代表底层集合绝不被其他引用修改。可以用 `copy` 配合 `map` 更新目标项，或在明确需要时采用不可变集合；不必声称项目用了额外集合库。

**追问**：每次复制大列表是否有成本？有，要根据列表规模、更新频率测量；必要时优化状态粒度或数据结构。

**易错点**：`@Stable`、`@Immutable` 是对稳定性契约的承诺，不能用来掩盖可变对象；不要随意加注解「强行优化」。

<a id="q-c12"></a>
### C12｜P1：LaunchedEffect、DisposableEffect、rememberCoroutineScope 如何用？
**参考回答（原理，非实现声明）**：LaunchedEffect 将协程任务绑定到组合范围，key 变化时取消旧任务并重新启动；DisposableEffect 适合注册监听与解除注册；rememberCoroutineScope 常用于点击回调触发、且随组合范围结束而取消的 UI 协程。业务请求一般交给 ViewModel，避免 UI 重建改变业务任务寿命。

**追问**：`LaunchedEffect(Unit)` 真的只执行一次吗？仅在该次进入组合的生命周期内；离开再进入仍会执行。

**易错点**：key 选择不当会重复收集或重启；不要把长生命周期 Activity 引用交给更长寿命对象。

<a id="q-c13"></a>
### C13｜P0：单图、四图、多图如何布局，为什么这样做？
**参考回答（原简历）**：单图按宽高比展示，四图采用两列，其余多图采用三列，以保持信息流阅读的一致性。实现时根据容器宽度、列数和间距计算单元尺寸，并处理缺失或异常尺寸、超长图及占位状态。图片加载前后尺寸尽量稳定，避免列表跳动。

**追问**：长列表里嵌套网格一定要用 LazyVerticalGrid 吗？不一定。单条动态图片数量有限，可用普通布局；同方向无限约束的嵌套滚动需要特别处理。

**易错点**：不要原尺寸解码所有高清图；UI 上的缩小显示不等于解码内存已经减小。

<a id="q-c14"></a>
### C14｜P0：Coil 解决了什么？怎样避免列表图片闪烁和内存压力？
**参考回答（原简历 + 原理）**：Coil 承担异步图片请求、解码与缓存，适配 Compose 图片展示。优化重点是提供合理的目标尺寸、稳定请求数据与占位布局，并区分内存缓存、磁盘缓存、网络请求。图片 URL 或变换参数无意义变化，会影响缓存命中。实际缓存配置要以项目依赖版本与代码为准。

**追问**：Glide 和 Coil 怎么选？都能做图片加载，结合 UI 技术、已有生态和实际需求选；不是 Coil 必然更快。

**易错点**：用了图片库不等于不会 OOM；不能把 Coil 的缓存命中率当作自己测过的项目成绩。参考：[Coil Compose 文档](https://coil-kt.github.io/coil/compose/)。

<a id="q-c15"></a>
### C15｜P1：发布、点赞、删除遇到重复操作与失败如何设计？
**参考回答（原理/改进）**：先明确操作是否允许并发。点赞可选择请求成功再更新，或乐观更新失败回滚；两者都要解决快速连点和乱序响应。发布/删除需要区分处理中、成功和失败，防止重复提交；跨重试去重通常还需要服务端幂等支持。原简历有这些功能，但不能据此推断已经实现了完整并发控制。

**追问**：刷新与点赞并发会覆盖怎么办？明确合并规则，例如按服务端版本、操作序列或保留未完成本地操作；不能仅凭最后一个响应覆盖全部列表。

**易错点**：禁用按钮只能减少 UI 重复提交，不代表端到端幂等。

### 三、Flow、协程与生命周期

<a id="q-c16"></a>
### C16｜P0：StateFlow 为什么适合 UiState？有什么容易忽略的语义？
**参考回答**：StateFlow 有当前值，新订阅者能收到最新状态，适合表达「现在页面是什么」。它按 equals 合并相同值，慢消费者可能跳过中间状态，因此不适合记录每一次事件。更新复杂对象应生成新快照；并发读改写可用 `update`，但更新函数应避免埋点、写库等副作用。

**追问**：连续发两个相同错误文本会怎样？相同状态可能不产生新通知；需要区分持续错误状态与每次提示事件的模型。

**易错点**：StateFlow 的线程安全不意味着其内部可变对象也安全。参考：[Kotlin StateFlow API](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/-state-flow/)。

<a id="q-c17"></a>
### C17｜P0：SharedFlow 的 Effect 是否保证只消费一次？
**参考回答**：不保证。原简历用 SharedFlow 表达 Snackbar、滚动等 Effect，但它是广播热流，不是带确认的可靠消息队列。`replay=0` 时，没有订阅者期间发出的值可能丢失；增加 replay 又可能在重新订阅时重复处理。`extraBufferCapacity` 也不是为不存在的订阅者永久留存消息。必须按事件重要性选择策略。

**追问**：支付或发布结果怎么办？重要结果应反映在可恢复的业务状态中；必要时引入事件标识和确认机制。轻量提示可以明确接受丢失，不能假称天然可靠。

**易错点**：「一次性」描述业务意图，不是投递保证。参考：[SharedFlow API](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/-shared-flow/)、[Android UI 事件指南](https://developer.android.com/topic/architecture/ui-layer/events)。

<a id="q-c18"></a>
### C18｜P0：页面退出后 Flow 会自动停止收集吗？
**参考回答（原理）**：取决于收集范围与生命周期策略。Compose 展示状态可使用 `collectAsStateWithLifecycle`；传统 UI 常在 `repeatOnLifecycle` 块内收集。当生命周期不满足条件时，收集被取消，恢复后重新启动。直接在 lifecycleScope 中 launch 后 collect，不等价于仅在可见时收集。取消 UI 订阅是否停止上游，还取决于上游实现和共享策略。

**追问**：多个 Flow 怎么收集？在 repeatOnLifecycle 块内分别启动子协程，避免第一个无限 collect 阻止后续代码。

**易错点**：viewModelScope 随 ViewModel 清理取消，不是 Activity 一到 onStop 就取消。参考：[Android Flow 指南](https://developer.android.com/kotlin/flow/stateflow-and-sharedflow)。

<a id="q-c19"></a>
### C19｜P0：suspend 是否代表在后台线程运行？为什么写库要切 IO？
**参考回答**：不是。suspend 表示函数可挂起，不自动切线程。阻塞数据库和文件 IO 不应堵住主线程，通常通过明确的调度器切换保持调用方安全；CPU 密集计算则更适合 Default。原简历有 IO 线程持久化，但不能因为外层使用协程就证明所有 Gson 序列化、数据库访问都已移出主线程。

**追问**：Retrofit 的 suspend 接口是否还要全部包 IO？要看实际调用是否阻塞；异步网络适配本身通常无需靠 IO 才能异步，但后续阻塞处理仍需安排。

**易错点**：协程不是线程，IO 也不意味着无限资源。切线程应有边界，不是每层随意切一次。

<a id="q-c20"></a>
### C20｜P1：协程取消、异常和并发怎么处理？
**参考回答**：结构化并发让子任务归属于作用域，父任务取消可以传递给子任务；取消通常是协作式的，长时间计算要检查取消。捕获异常时不能把 CancellationException 当普通网络错误吞掉。兄弟任务是否互相取消取决于普通 Job 或监督关系，监督也不等于异常自动消失。

**追问**：一个网络请求失败，能否继续显示缓存？可在 Repository 把可恢复失败映射为缓存结果，但用户取消操作不应被误判成网络失败再继续工作。

**易错点**：GlobalScope 容易让任务脱离页面与业务生命周期；`try/catch` 包住 launch 调用不等于捕获异步体的全部异常。

<a id="q-c21"></a>
### C21｜P0：旋转屏幕与进程死亡有什么差别？
**参考回答**：配置变化通常导致 Activity 重建，正确作用域内的 ViewModel 可被保留；进程死亡则整个内存状态消失。恢复时要依靠系统保存的轻量状态与磁盘/服务器数据重新构建，而不是期待同一个 ViewModel 还存在。onDestroy 不保证总能执行，所以关键数据不能等退出时才保存。

**追问**：输入中的草稿怎么恢复？短小文本可通过保存状态机制处理，复杂或长期草稿应持久化并保存草稿 ID。

**易错点**：仅测旋转屏幕不等于验证了进程死亡恢复；强行结束应用与系统后台回收的恢复条件也不同。

<a id="q-c22"></a>
### C22｜P1：Activity 和 Fragment 生命周期有哪些实际坑？
**参考回答**：Activity 的创建、开始、恢复、暂停、停止、销毁对应不同可见性和交互阶段。Fragment 还有独立的 View 生命周期，Fragment 实例可能仍在而它的 View 已销毁。与 View 绑定的观察应使用 viewLifecycleOwner，ViewBinding 等引用在 onDestroyView 释放，避免更新旧 View 和泄漏。

**追问**：从一个页面进入半透明页面，回调一定和进入全屏页面一样吗？不一定，要根据是否失去焦点、是否不可见分析。

**易错点**：不能把 onPause 当作完整业务持久化的可靠唯一入口；也不要把所有问题归因于「生命周期乱了」。

### 四、缓存、数据库与网络

<a id="q-c23"></a>
### C23｜P0：FeedLine 为什么用 SQLiteOpenHelper + Gson？Room 在哪里？
**参考回答（原简历）**：FeedLine 的原简历写的是 SQLiteOpenHelper 管理 SQLite 存储、Gson 做对象与 JSON 转换，而不是 Room。该方案依赖少、容易落地，但需要自己处理建表、迁移、游标关闭与线程边界；JSON 形式的复杂字段也不方便做精细 SQL 查询。Room 可以作为另一项目经验或改进选项，不能混写为现有实现。

**追问**：Gson 是数据库吗？不是，它负责序列化。JSON 字段新增、改名、默认值与旧缓存兼容都要考虑。

**易错点**：直接丢弃所有旧缓存有时可接受，但涉及用户未上传草稿时不能随意删库重建。

<a id="q-c24"></a>
### C24｜P0：网络失败回退缓存，算离线优先吗？
**参考回答**：它至少说明有降级能力，但不自动等于完整 offline-first。完整离线能力还涉及本地事实来源、同步队列、冲突解决、重试和删除标记。当前可诚实介绍为「网络异常时读取缓存，改善弱网下的可用性」。需要补答首次启动无缓存、缓存损坏、旧数据提示与刷新失败时保留已有内容等情况。

**追问**：缓存多久失效？若未实现过期策略，应明确说明现状，再提出时间戳或版本校验方案。

**易错点**：不要把读缓存成功显示成网络刷新成功；不能宣称离线点赞会自动可靠同步，除非确有实现。

<a id="q-c25"></a>
### C25｜P1：Room、SQLite、DataStore 分别适用什么数据？
**参考回答（原理）**：SQLite 是关系型存储引擎；SQLiteOpenHelper 提供数据库创建与版本管理入口。Room 在 SQLite 之上提供实体、DAO、查询检查和迁移等支持，适合结构化、多表与查询场景。DataStore 适合偏好或较小的类型化配置，不能替代需要关系查询、局部记录更新的大型业务数据库。

**追问**：Room 加 suspend 就万事大吉吗？仍要注意查询规模、索引、事务、迁移与数据映射开销。

**易错点**：不要给 FeedLine 强加 Room；不要把设置存储当成密码保险箱，敏感信息需要专门的安全设计。参考：[DataStore 官方指南](https://developer.android.com/topic/libraries/architecture/datastore)。

<a id="q-c26"></a>
### C26｜P1：索引、事务、WAL 能解决什么问题？
**参考回答（原理）**：索引减少特定查询的扫描，但占空间并增加写入维护成本；应围绕真实 WHERE、排序与查询计划设计。事务让一组写入具有一致的提交边界。WAL 改变日志与并发读写方式，常能改善读写并存，但仍不意味着多个写事务可以无限并行，也不能代替正确的事务设计。

**追问**：如何验证索引生效？结合 EXPLAIN QUERY PLAN、数据规模与耗时，不以「建了索引」直接推断性能提升。

**易错点**：别对每一列都建索引；批量缓存写入放同一事务时，也要避免事务过大长期占用资源。

<a id="q-c27"></a>
### C27｜P0：Retrofit 与 OkHttp 是什么关系？
**参考回答**：Retrofit 把 HTTP 接口声明映射为请求和响应，并通过转换器、调用适配器与业务类型连接；常见底层 HTTP 客户端是 OkHttp，它处理连接、拦截器、请求执行等。Gson 可以用于 JSON 转换，但业务错误码、认证失效、空数据与 HTTP 错误仍要由应用明确处理。

**追问**：接口返回 HTTP 200 就成功了吗？不一定，还要检查业务语义与响应结构；反之异常也要区分网络、HTTP、解析与业务失败。

**易错点**：不要把所有失败统一展示成「网络不好」，也不要把敏感请求头输出到日志。

<a id="q-c28"></a>
### C28｜P1：超时、重试、缓存、拦截器怎么解释？
**参考回答（原理）**：连接超时、读写超时与整次调用预算关注不同阶段，应根据请求类型设置。重试需考虑错误类型、次数、退避和幂等性；发布类操作不能随意重试制造重复数据。应用数据库缓存与 HTTP 缓存不是同一层，前者由业务定义，后者还受到响应头等缓存语义约束。拦截器适合统一添加必要请求信息和观测耗时。

**追问**：令牌刷新时多个请求同时失败怎么办？可集中协调刷新并限制重放，避免并发刷新风暴；若项目未实现，应作为设计题回答。

**易错点**：不能说 OkHttp 自动重试就保证所有请求可靠、恰好执行一次。

### 五、语言、Android 组件与工程能力

<a id="q-c29"></a>
### C29｜P0：Kotlin 与 Java 的差别，哪些与你项目直接有关？
**参考回答**：Kotlin 提供可空类型、数据类、扩展函数、密封类型和协程等表达能力，适合建模 UiState/Intent；Java 与 Kotlin 在 Android/JVM 场景可互操作。可空类型减少部分空指针风险，但 `!!`、平台类型、初始化问题仍可能出错。data class 的 copy 通常是浅复制，内部可变集合并不会自动深复制。

**追问**：`==` 与 `===`？Kotlin 中前者结构相等，后者引用相同；Java 对象 `==` 比较引用，内容比较通常使用 equals。

**易错点**：扩展函数不是修改原类或动态覆盖成员；`val` 只禁止重新赋值，不保证对象内部不可变。

<a id="q-c30"></a>
### C30｜P1：Dart、Future、Stream、Isolate 与 Kotlin 协程怎么比较？
**参考回答（原理）**：Future 表达一个未来结果，Stream 表达异步序列；async/await 让异步控制流更易读，但不会自动把 CPU 密集任务移到另一个执行环境。Dart 的 Isolate 有隔离的内存空间，通过消息通信；Kotlin 协程则通常共享所在进程内的对象，需要同步管理共享状态。两者都要考虑取消、错误和 UI 生命周期，但 API 不可一一机械对应。

**追问**：Flutter 与 Kotlin 通信怎么做？可通过平台通道等机制定义方法、数据格式、错误与线程边界；具体 SSH Mobile 桥接实现以项目章节为准。

**易错点**：不要说每个 Future 都对应一条线程，或 Flutter 全部代码只运行在一个线程。

<a id="q-c31"></a>
### C31｜P1：Service 是不是后台线程？启动式与绑定式有什么区别？
**参考回答**：Service 是 Android 组件，默认并不自带工作线程，其回调通常仍在所属进程的主线程。启动式关注服务任务自身的启动与停止，绑定式提供客户端与服务交互；二者可以组合。独立进程需要显式配置，不由 Service 名称决定。具体后台执行限制与前台服务类型要按目标系统版本核对。

**追问**：音乐播放放 Service 就能保证永不被杀吗？不能；还需要符合平台要求的前台运行、通知与恢复策略。

**易错点**：不要在 onStartCommand 阻塞做网络请求，也不要把 Service 等同于保活工具。

<a id="q-c32"></a>
### C32｜P1：Binder、AIDL、IPC 如何讲清楚？
**参考回答（原理，非 FeedLine 实现）**：IPC 是进程间通信。Binder 是 Android 常用 IPC 机制；AIDL 用接口描述生成通信代码，使跨进程方法调用具有明确参数与返回类型。跨进程存在序列化、线程切换、进程死亡等成本，不是普通内存内调用。服务端远程调用可能来自 Binder 线程池，操作共享状态和回调 UI 都要处理线程边界。

**追问**：传大图片怎么办？避免把大对象直接塞进事务，可传 URI、文件描述符等合适句柄；同时校验调用权限和数据访问范围。

**易错点**：AIDL 不自动让业务线程安全；oneway 也不保证业务执行成功。音频服务案例若来自 Word Crush，应明确项目归属。参考：[AIDL 官方指南](https://developer.android.com/develop/background-work/services/aidl)。

<a id="q-c33"></a>
### C33｜P2：RecyclerView、DiffUtil、Glide 与 Compose 有哪些可迁移的思路？
**参考回答（原理/其他项目）**：RecyclerView 重用 ViewHolder，DiffUtil 比较旧新列表并计算更新；要区分「是否同一业务项」与「内容是否相同」。Compose Lazy 列表也关注元素身份与按需组织，但机制不是直接套用 ViewHolder。Glide 与 Coil 都需要考虑图片尺寸、缓存和生命周期。共同能力是定位列表更新、图片加载与主线程开销。

**追问**：DiffUtil 期间修改同一份列表会怎样？比较依据可能失效；应提交稳定快照，避免在比较过程中改动数据。

**易错点**：不能把 RecyclerView/DiffUtil/Glide 写成 FeedLine 的已有优化，它们属于其他项目或通用知识。

<a id="q-c34"></a>
### C34｜P1：Gradle 依赖冲突怎么定位？
**参考回答**：先区分版本选择冲突、重复类、资源冲突、二进制不兼容和构建插件兼容问题。通过依赖树与 dependencyInsight 找到传递依赖路径，再根据 SDK 兼容要求统一版本、排除确实多余的传递依赖或升级相关库。修改后既要验证编译，也要验证初始化和关键业务路径。

**追问**：为什么不直接 force 一个版本？强制选择可能让另一 SDK 运行时缺方法或缺类，必须证明调用方兼容。

**易错点**：清缓存可以帮助排除构建环境问题，但不是依赖治理的根因修复；具体 AndroidX 案例见实习章节。

<a id="q-c35"></a>
### C35｜P1：Git 如何支撑定位问题和团队开发？
**参考回答**：用 log、show、diff 理解变更，结合 blame 追踪代码上下文；可重复复现的回归问题可用 bisect 缩小引入提交范围。merge 保留分叉历史，rebase 重新组织提交基础并改变提交标识；公共历史不应随意重写。解决冲突后要运行相关测试，而不是只让文件没有冲突标记。

**追问**：如何证明一次优化确实来自某次提交？保留前后版本、同一测试条件、指标采集方法及结果，排除同时混入的其他变更。

**易错点**：commit 标题是线索不是性能证据；不能凭「optimize」提交名生成提升百分比。

<a id="q-c36"></a>
### C36｜P1：Compose UI Test 和 Flutter Test 各测什么？
**参考回答（原理）**：Compose UI Test 通过语义节点查找元素、执行操作并断言展示结果；ViewModel/UseCase 逻辑可用普通单测与 fake Repository 隔离测试。Flutter 常区分单元测试、Widget 测试和集成测试。好的项目测试应覆盖网络失败回退、空列表、重复操作、状态恢复等风险，而不只是点击按钮不崩溃。

**追问**：异步测试为什么不直接 sleep？固定等待易慢且不稳定，应使用框架同步机制或可控制的调度器与假依赖，明确等待条件。

**易错点**：测试命令跑通不等于关键场景覆盖；不能虚构覆盖率、测试数量或 CI 通过记录。参考：[Compose 测试指南](https://developer.android.com/develop/ui/compose/testing)。

### 六、基础知识与综合追问

<a id="q-c37"></a>
### C37｜P1：如何从数据结构解释信息流的性能取舍？
**参考回答**：列表按顺序展示适合顺序结构，按 ID 查找可辅以 Map；ArrayList 随机访问通常为 O(1)，中间插入/删除一般需要移动元素。HashMap 查找通常期望 O(1)，不是无条件最坏 O(1)。LRU 可用哈希表与双向链表组合维护查找与最近访问顺序，但还要考虑容量、对象大小与线程安全。

**追问**：为了点赞查找建 Map 是否一定值得？取决于列表长度、频率与维护成本；先确定瓶颈，不为了写算法而增加一致性负担。

**易错点**：复杂度不能直接等于实际耗时，图片解码或主线程 IO 可能远比一次列表遍历更重。

<a id="q-c38"></a>
### C38｜P1：进程、线程、死锁、ANR、掉帧怎么区分？
**参考回答**：进程是资源隔离边界，线程是进程内执行单元，线程间通常共享内存。死锁是相互等待形成无法推进的依赖；ANR 是特定组件在平台规定条件下未及时响应；掉帧是未能按刷新节奏完成绘制。它们相关但不等价，主线程长任务、锁等待、Binder 阻塞都可能造成问题。

**追问**：怎么排查？先拿现场堆栈和跟踪，确定主线程在计算、IO、等待锁还是远程调用，再找持锁者或耗时来源。

**易错点**：不要死背「所有 ANR 都是 5 秒」；不同触发类型和平台条件不同。60 Hz 下约 16.7 ms 是一帧节奏，不是所有设备固定值。

<a id="q-c39"></a>
### C39｜P0：面试官让你现场设计 FeedLine 测试，你怎么回答？
**参考回答（方案，不冒充已完成）**：按链路分层：UseCase 测操作规则，Repository 测网络成功、异常回退、有/无缓存和损坏缓存，ViewModel 测加载到结果的状态变化与连续操作，UI 测混合媒体、点赞反馈和错误提示。补旋转、后台返回、进程恢复、弱网与大图片场景。性能对比需要固定设备、构建类型、数据量和操作脚本。

**追问**：怎么测试 SharedFlow 丢事件风险？覆盖订阅前发射、订阅暂停、恢复订阅和多个订阅者，并对照项目配置判断是否符合产品期望。

**易错点**：给出的测试计划要和现有测试区分，不能回答成「这些我都覆盖了」。

<a id="q-c40"></a>
### C40｜P0：如果再迭代一周，最先改什么？有什么没有做？
**参考回答**：我会先核对真实风险而非换技术栈：补状态与缓存边界测试，明确重要操作与瞬时 Effect 的职责，检查快速点赞/刷新时的并发一致性，再根据跟踪结果处理列表与图片瓶颈。如果缓存结构逐渐复杂，可以评估 Room 和迁移，但不为了简历名词强行重构。目前没有代码证据的分页、自动离线同步、可靠事件队列和定量性能收益，我不会称为已经实现。

**追问**：如何体现竞争力？展示一条可运行、可解释、可测试的真实闭环，比列出更多框架更有说服力；与 SSH Mobile 的跨语言、协议和 Agent 能力形成互补。

**易错点**：不要否定旧方案来显得懂架构。说明当时约束、当前规模、改进收益与迁移成本。

### 七、Java / Kotlin 与 Android 机制补充追问

> A41–A48 全部是围绕简历技能的**通用原理与设计题**，不表示 FeedLine 已经实现了这些机制或全部测试。

<a id="q-c41"></a>
### C41｜P1：Handler、Looper、MessageQueue 如何协作？为什么能切回主线程？
**参考回答**：Handler 关联某个 Looper，post 或 sendMessage 将任务放入对应消息队列；Looper 在所属线程循环取出并分发消息，因此执行线程由 Looper 决定，不由发送线程决定。`Handler(Looper.getMainLooper())` 明确把回调交给主线程。一个回调耗时很长，会阻塞该线程后续消息和 UI 工作；队列中没有消息时的等待不同于业务代码把主线程长时间卡住。

**追问**：postDelayed 能精准定时吗？只能安排不早于指定条件的执行机会，仍受消息排队、线程繁忙与系统休眠等因素影响，不能当可靠后台定时器。

**易错点**：Handler 不会自动创建新线程；主线程 Looper 的循环也不意味着必然 ANR。参考：[Handler API](https://developer.android.com/reference/android/os/Handler)。

<a id="q-c42"></a>
### C42｜P1：有 GC 为什么还会泄漏？强、软、弱、虚引用怎么联系到项目？
**参考回答**：GC 回收不可达对象，不知道业务上「这个页面已经不用了」。若单例、监听器、未结束任务或队列中的 Runnable 持有 Activity，页面即使销毁仍可能从 GC Roots 可达。强引用阻止对象因不可达而回收；弱引用不阻止回收；软引用受内存策略影响，不宜作为可预测缓存方案；虚引用通常配合引用队列观察回收相关通知，不能用它读取对象。

**追问**：怎样查页面泄漏？重复进入退出页面，结合堆快照和引用链定位意外长寿命持有者，再验证解除监听、取消任务或缩短引用作用域后是否释放。

**易错点**：给 Activity 换成 WeakReference 不能代替正确取消任务；图片缓存过大和真正泄漏也要区分。

<a id="q-c43"></a>
### C43｜P1：synchronized、volatile、AtomicInteger 分别保证什么？
**参考回答**：synchronized 通过同一监视器实现互斥，并建立对应可见性保证，适合保护一组必须一起成立的状态。volatile 关注读写可见性与相应顺序约束，不让 `count++` 这样的读改写自动原子化。AtomicInteger 等提供单变量原子更新；若要同时维护多个字段的不变量，通常仍需要锁、不可变整体状态或其他协调方式。

**追问**：协程只用主线程就完全不用管并发吗？即使没有并行执行，挂起点之间仍可能发生逻辑交错；涉及跨线程共享数据时更要明确同步。协程互斥还可用 Mutex，但不能把所有锁等同。

**易错点**：不要锁住共享资源后执行长时间网络或阻塞调用；`volatile List` 不会让列表内部操作线程安全。参考：[Java 原子操作与可见性](https://docs.oracle.com/javase/tutorial/essential/concurrency/atomic.html)。

<a id="q-c44"></a>
### C44｜P1：sealed、enum、interface 怎么选？扩展函数有哪些边界？
**参考回答**：UiState 若存在 Loading、Success(data)、Error(reason) 等携带不同数据的分支，sealed 类型适合表达受控的变体集合，配合 when 检查覆盖；enum 更适合固定枚举项，interface 则适合开放能力契约。扩展函数适合为现有类型增加便捷调用语法，但不是修改原类，也不能直接访问原类私有成员，其解析基于静态接收者类型；同签名成员函数优先。

**追问**：sealed 是否意味着所有子类必须写在同一个文件？不是简单的同文件限制；直接子类通常受同模块、同包等约束，多平台还需看对应规则。

**易错点**：不要用一个塞满 nullable 字段的数据类表达所有互斥状态，也不必为了「设计模式」把每个布尔值变成密封层级。参考：[Kotlin sealed 文档](https://kotlinlang.org/docs/sealed-classes.html)。

<a id="q-c45"></a>
### C45｜P2：泛型为什么需要 in/out？reified 能解决什么、不能解决什么？
**参考回答**：可变容器通常不能简单把 `MutableList<Dog>` 当作 `MutableList<Animal>`，否则可能写入其他 Animal。`out T` 适合对外生产 T 的协变接口，`in T` 适合消费 T 的逆变接口；Java 常用 `? extends`、`? super` 表达使用点约束。JVM 泛型通常存在类型擦除，Kotlin 的 inline + reified 可在调用点保留使用类型参数所需的信息，方便 `is T` 或获取类型相关对象。

**追问**：reified 能直接判断一个任意列表的所有元素都是 String 吗？不能把它当成任意嵌套泛型运行时校验器，集合内部泛型参数仍需具体策略验证。

**易错点**：`List<*>` 不是随意可写的 `List<Any?>`；Gson 解析参数化类型时要提供合适的类型信息，不能只传原始 List 类。参考：[Kotlin 泛型文档](https://kotlinlang.org/docs/generics.html)。

<a id="q-c46"></a>
### C46｜P2：Android 的 Java/Kotlin 跑在 JVM 上吗？与 Dart 有什么差异？
**参考回答**：Java/Kotlin 的 Android 常规构建会经过 JVM 字节码相关阶段，再转换成 DEX，由 Android 的 ART 管理运行；不能直接说 Android 就是桌面 HotSpot JVM。ART 有运行时与编译优化机制，具体策略随版本变化。Flutter 的 Dart 代码使用自己的运行时与构建链路，在移动端开发和发布模式下采用不同编译策略，不是把 Dart 编成 Java 再交给 ART；插件中的 Kotlin/Java 部分仍走 Android 路径。

**追问**：为什么不能用 Flutter debug 的卡顿结果证明线上性能差？debug 为调试和热重载服务，应使用真机 profile 等合适模式分析，并固定条件。

**易错点**：不要说「ART 永远纯 AOT、Dart 永远解释执行」。参考：[ART 概览](https://source.android.com/docs/core/runtime)、[Flutter 构建模式](https://docs.flutter.dev/testing/build-modes)。

<a id="q-c47"></a>
### C47｜P1：FeedLine 有选图、拍照、录像，权限和 Activity Result 应该怎么设计？
**参考回答（设计题）**：先区分系统媒体选择器、调用外部相机应用、应用内自行使用相机三种路径，再确定最小权限需求，不能默认申请整个媒体库和相机权限。媒体选择可优先考虑系统 Photo Picker；结果通过 Activity Result Contract 解析，处理取消、失败和空结果。应用内直接访问相机/麦克风则要按实际功能与系统版本处理运行时授权、拒绝和功能降级。

**追问**：进入外部相机期间进程被回收怎么办？结果回调应在重建时按框架要求稳定注册，另外保存待处理拍摄目标等恢复信息；不要只把临时 URI 放在局部变量。

**易错点**：不能未经代码核对就说项目使用了 Photo Picker；外部相机路径与自己调用相机 API 的权限要求不同。参考：[Photo Picker](https://developer.android.com/training/data-storage/shared/photo-picker)、[Activity Result](https://developer.android.com/training/basics/intents/result)。

<a id="q-c48"></a>
### C48｜P1：图片和视频返回 content URI 后怎么读取？离开页面后还能用吗？
**参考回答（设计题）**：content URI 是内容访问标识，不一定对应可直接打开的真实文件路径，应通过 ContentResolver 打开流或文件描述符，并及时关闭。访问权限的寿命取决于来源与授权；需要长期或后台使用时，应按返回契约申请可持久化授权，或在允许的范围内复制到应用私有存储，不能把所有 URI 都当永久有效。上传前检查 MIME、大小和读失败，避免一次性把大视频全部读入内存。

**追问**：拍摄原图如何交给外部相机写入？可预先准备受控输出 URI，并按调用契约授予必要权限；失败或取消后处理临时文件。视频预览还要管理播放资源、页面离开后的暂停/释放与恢复位置。

**易错点**：`uri.path` 不是通用真实路径；存下 URI 字符串不代表保留了读取授权，持久化授权也不保证源文件永不被删除。参考：[Photo Picker 的持久访问说明](https://developer.android.com/training/data-storage/shared/photo-picker)。

<a id="q-i02"></a>
### I02｜SDK 和普通 App 开发有什么不同？

**回答要点**：SDK 运行在宿主 App 内，不能假设自己独占依赖版本、进程、初始化顺序和生命周期。公共 API 要稳定，不能随意要求业务工程跟随内部实现变化。错误处理和日志应帮助宿主定位问题，又不能暴露凭据或敏感信息。

**结合实习回答**：“我遇到的典型差异是，渠道 SDK 在独立 Demo 中能跑，不代表放进内部游戏工程后没有依赖冲突，所以需要结合宿主的依赖和核心业务流程验证。”

**深入追问**：初始化为什么需要幂等？为什么不能长期持有 Activity？

- 幂等是为了避免宿主重复调用或页面重建时重复注册回调、重复初始化。
- 长生命周期对象持有已销毁 Activity 会造成泄漏；但需要界面能力的操作也不能机械地全部改用 Application Context。
- 以上是一般设计原则，不直接声称已在实习中实现某一种管理框架。

<a id="q-i03"></a>
### I03｜接入一个渠道 SDK，你会如何拆解工作？

**参考流程，不代表每一步均已实际执行**：

1. 明确 SDK 版本、最低系统要求、依赖、渠道参数和业务接口变化。
2. 对齐初始化、登录、支付、退出和生命周期转发要求。
3. 检查 Manifest 合并、组件配置、混淆规则、依赖冲突及签名配置。
4. 在测试工程验证，再进入真实宿主；覆盖成功、取消、失败、重复操作和进程重建等场景。
5. 保存渠道、SDK、宿主版本与验证结果的对应关系。

**追问**：如果渠道回调与内部接口定义不一致怎么办？

“要区分业务结果和技术错误，做明确的字段及状态映射，保留必要错误信息，并防止一次操作产生重复完成回调。”不要宣称自己设计了统一适配层，除非确实有该层及个人实现证据。

<a id="q-i04"></a>
### I04｜登录、支付和生命周期适配，分别容易出什么问题？

**回答要点**：

- 登录：成功、失败、取消状态映射不一致；回调线程不同；切后台或 Activity 重建后回调目标失效。
- 支付：重复点击、重复回调、订单状态不同步、网络中断。**客户端回调不应被当作最终到账的唯一可信依据**，具体业务以服务端确认链路为准。
- 生命周期：宿主没有按渠道要求转发事件、注册与注销不成对、页面销毁后异步结果仍更新旧页面。

**追问**：你自己处理过哪一个？

先讲真实的渠道和现象；目前已确认的是 AndroidX 兼容问题，不要为了完整而现场编造支付故障。若没有独立处理支付异常，可以说“我做过接入与适配，订单最终确认由服务端链路负责；我能说明客户端应防范的问题，但不会把它说成我处理过的线上事故”。

<a id="q-i05"></a>
### I05｜AndroidX 是什么？“将 Android 升级到 AndroidX”准确吗？

**可直接回答**：“更准确的说法是将工程及依赖从旧 Android Support Library 体系迁移到 AndroidX，不是升级 Android 操作系统。迁移涉及包名、依赖坐标及第三方库兼容。我在实习中推进了相关迁移，并处理渠道 SDK 与内部工程的依赖冲突。”

**原理与追问**：AndroidX 的命名空间是 `androidx.*`；迁移不能只改源码 import，还要查看资源、XML、传递依赖和最终产物。不要把 AndroidX、Jetpack、Android 系统版本、AGP 版本混为一谈。[官方迁移说明](https://developer.android.com/jetpack/androidx/migrate)

**待补事实**：迁移前具体有哪些 Support 库？哪个渠道或内部模块引入冲突？报错是编译失败、重复类还是运行时找不到方法？这些才是面试官会据此深挖的真实证据。

<a id="q-i06"></a>
### I06｜怎样定位依赖冲突？Gradle 依赖树怎么看？

**参考回答**：“先保留完整报错，确定失败阶段和具体类、方法或依赖，再检查对应构建变体的依赖图，找出直接依赖和传递依赖来源。然后查某个模块为什么被选到该版本，而不是直接把所有库都升级到最新。”

```bash
# 以下以 app/debug 为例，实际模块与变体名称需要替换
./gradlew :app:dependencies --configuration debugRuntimeClasspath
./gradlew :app:dependencyInsight --dependency <group-or-module> --configuration debugRuntimeClasspath
```

`dependencies` 用来查看依赖关系，`dependencyInsight` 用来追踪指定依赖的引入路径和版本选择原因。编译期问题也应查看对应的 compile classpath。命令是可用排查方法，不代表已经证实你当时使用过。[Gradle 官方依赖诊断说明](https://docs.gradle.org/current/userguide/viewing_debugging_dependencies.html)

**追问**：依赖树看起来只有一个版本，为什么还报 Duplicate class？

可能不同 Maven 坐标的包包含同一个类，或者本地 JAR/AAR 内嵌了重复类；不能只看同坐标版本冲突。

<a id="q-i07"></a>
### I07｜exclude、版本统一、强制版本和 Jetifier 应该怎么选？

**参考回答**：“先确认冲突来源和 API 兼容性，再选择最小修改。可升级到兼容版本、去掉明确冗余的传递依赖，或统一依赖约束。强制版本只能改变解析结果，不能证明运行时兼容；排除依赖也可能把真实需要的类一起删掉。”

**Jetifier 的边界**：它用于兼容仍引用旧 Support Library 的第三方依赖，不是通用冲突修复器；已经原生支持 AndroidX 的依赖通常不需要依靠它，开启它还可能增加构建成本。**项目是否使用 Jetifier 尚未确认，不要说“我通过 Jetifier 解决了冲突”。**[Android 官方说明](https://developer.android.com/jetpack/androidx/migrate)

**追问**：为什么编译成功不等于解决？

因为调用方编译时期待的类或方法，可能与实际运行时加载的版本不匹配；反射、资源、混淆和特定业务分支的问题也可能只在运行时出现。

### I08｜AndroidX 迁移案例如何用 STAR 讲？

**可直接使用的真实边界版**：

- **S**：渠道 SDK 升级和内部工程集成中，需要迁移到 AndroidX，同时出现依赖兼容问题。
- **T**：我的任务是推进迁移并处理冲突，保障 SDK 与内部工程能够兼容。
- **A**：我参与修改工程依赖和相关适配，处理渠道依赖与内部工程的冲突。具体引入路径、修改项和验证方式，我会结合当时记录补充。
- **R**：完成了相关迁移和兼容处理。这里不编造构建耗时下降、故障率降低或覆盖率提升的数据。

**面试前必须补成一个具体实例**：`渠道/模块 → 旧依赖 → 冲突报错 → 哪两条引入路径 → 修改哪处 → 哪些场景验证`。如果只能说“解决了各种冲突”，可信度仍然不够。最好找一条脱敏提交或工单，不需要泄露公司代码。

<a id="q-i09"></a>
### I09｜你做的 Frida + Python 工具是怎样工作的？

**可直接回答**：“工具用于我们有授权的测试环境，对新版本 SDK 和新游戏做上线前检测。核心思路是在运行时观察敏感 API 调用，并由 Python 配合执行和汇总检测信息。我通过这类检测发现过频繁获取设备 ID 的问题。”

**原理补充**：Frida 可以在目标进程运行期间插入观测逻辑；脚本负责采集调用信息，宿主程序可接收消息并组织结果。Java 层 Hook 需要考虑类加载时机、方法重载和原方法调用，避免观测代码改变原有行为。具体工具是否记录了完整堆栈、是否自动驱动 UI、是否自动生成报告，需要按你的真实实现回答。[Frida JavaScript API](https://frida.re/docs/javascript-api/)

**不要扩大为**：“我建设了覆盖所有 API 的自动化合规平台”“接入了 CI 阻断发布”“完整覆盖 native 层”，除非有真实实现。

<a id="q-i10"></a>
### I10｜为什么用动态检测？静态扫描不够吗？

**参考回答**：“静态扫描能帮助发现潜在调用点，但看到引用不代表运行时一定调用；动态检测能把调用和实际操作场景联系起来，观察同意前后、前后台切换或某个业务动作下是否发生敏感访问。两者互补。”

**局限**：动态检测只覆盖实际执行到的路径。未触发功能、其他进程、native 调用、动态加载和 Hook 未成功，都可能造成漏报；没有日志不等于不存在调用。

**追问**：怎样证明工具真的生效？

在自有测试代码中安排一个可控的已知调用作为校验，检查脚本加载成功、目标进程与方法签名正确，再核对正常业务流程是否仍工作。这个办法是建议验证方式，不是已确认的历史步骤。

<a id="q-i11"></a>
### I11｜怎么证明“频繁获取设备 ID”，而不是凭感觉？

**参考回答**：“需要给出可复现的观测窗口和操作步骤，把调用次数与时间、业务阶段、调用来源对应起来，而不是只说次数很多。”

**建议采集字段**：测试包及 SDK 版本、系统版本、设备型号、测试场景、隐私同意状态、前后台状态、API 标识、时间戳、调用栈摘要。原则上不必保存真实设备 ID 的原值；做脱敏、访问控制及必要的保留期限管理。

**判断方法**：相同场景重复执行，统计单位时间调用次数、间隔及相同堆栈的重复情况，区分用户操作触发与无操作情况下的重复请求。

**事实边界**：你目前只确认“发现频繁获取”。实际是哪个标识、哪个方法、多少次、持续多久、是否在后台、是否发生在同意前，都需要补充，不能把问题描述自动扩大成上述所有情形。

<a id="q-i12"></a>
### I12｜发现频繁调用后，怎么定位到责任模块？

**参考排查链路**：`检测时间点 → 具体 API → 调用栈 → 业务动作 → SDK/游戏模块及版本 → 可复现路径`。调用栈中关注第一个可解释的业务或 SDK 调用者；线程和时间序列可帮助区分定时任务、重试、重复初始化等候选原因。

**关键判断**：定时轮询、重复初始化、每次请求重取、错误重试等只是**可能原因**。你尚未确认实际根因，不要选一个听起来合理的故事当作亲身经历。

**追问**：调用栈被混淆怎么办？

利用匹配版本的 mapping、构建信息和模块边界辅助还原；必须匹配具体产物，不能拿另一个版本的映射猜测。拿不到第三方源码时，应提供可复现操作和脱敏证据给负责团队或渠道厂商协查。

<a id="q-i13"></a>
### I13｜隐私问题应该怎样修改、怎样验证？

**目前安全回答**：“我已确认的工作是上线前检测并定位风险。具体修复方案和复测结论，我需要核实当时记录后再准确描述，不会把通用方案说成已经做过。”

**可讨论的技术方案，不能直接当成履历**：

- 不必要的采集直接去掉，必要的采集按实际业务条件控制触发。
- 检查初始化与用户选择的关系，避免仅延后启动时间却未改变访问条件。
- 若业务确有必要，可评估合理缓存、去重或频率控制，但缓存本身涉及数据存储，**不等于自动解决合规问题**。
- 第三方问题可评估升级、调整配置、替换能力或推动厂商修复。

**复测矩阵**：首次安装、拒绝/同意、撤回选择（若产品支持）、冷启动、登录、切前后台、无操作停留；对比同一场景修改前后的调用证据，同时回归核心功能。保留版本与结论，不以“本次没抓到”宣称永久解决。

<a id="q-i14"></a>
### I14｜怎么谈隐私合规才准确？这个案例的 STAR 怎么写？

**更准确措辞**：“在新版本 SDK 和新游戏上线前，发现设备标识存在频繁访问的现象，作为隐私合规风险进行定位和反馈。”不直接说“只要频繁访问设备 ID 就一定违法”。判断还涉及标识类型、用途、必要性、授权及告知、平台规范等，技术检测与最终合规判断不是同一件事。

**STAR 事实版**：

- **S**：新版本 SDK 和新游戏上线前需要检查敏感信息访问行为。
- **T**：记录敏感 API 调用，提前发现并定位风险。
- **A**：基于 Frida 和 Python 开发检测工具，对测试场景中的敏感调用进行观察，发现频繁获取设备 ID 的问题。
- **R**：在上线前识别并定位了风险；当前不补写“减少了多少次”“完成整改”“通过监管检测”等未确认结果。

**面试官追问“最后解决了吗”**：必须补充真实事实。若你只负责检测定位，应直接说自己交付了哪些证据、由谁处理后续，而不是用“我们都解决了”绕开责任边界。

<a id="q-i15"></a>
### I15｜整体 SDK 崩溃率低于 0.25%，这个数字怎么算？

**可直接回答**：“这是整体 SDK 的指标，不是单一渠道的指标；我当时主要承担 SDK 的日常维护。但它是整体运行情况，不能说是我个人把崩溃率降低到了 0.25%。分母、统计周期和归因方式，我需要按原看板口径确认。”

**必须分清的几种口径**：

| 可能的指标 | 分子 / 分母示例 | 不能混淆的点 |
|---|---|---|
| 用户崩溃率 | 发生崩溃的去重用户 / 活跃用户 | 不等于崩溃次数比例 |
| 会话崩溃率 | 发生崩溃的会话 / 总会话 | 一位用户可能有多次会话 |
| 次数型比例 | 崩溃事件数 / 某类运行或调用次数 | 需解释重复事件与分母定义 |

以上是一般可能口径，不是在认定原看板使用哪一种。还需确认统计的是宿主全量崩溃还是归因到 SDK 的崩溃、时间窗口、Android 范围、样本量和版本范围。若拿不到口径，简历宜改成“结合整体 SDK 稳定性看板进行问题定位与维护”，不要留下无法解释的精确数字。

<a id="q-i16"></a>
### I16｜拿到一个线上崩溃，你怎么排查？pid/gid 是什么？

**参考流程**：先确定影响版本、渠道、设备及系统分布，再按异常类型与堆栈聚类；找变化点和复现条件，结合日志判断触发链路。修复后使用匹配场景回归，并在发布后观察同一问题是否仍出现、新版本样本是否足够。

**pid/gid 特别提醒**：简历里的这两个字段含义没有被确认。它们可能是业务标识，也可能在特定系统中另有定义。**不能看到 pid 就说进程 ID，更不能把 gid 直接说成 Linux 组 ID。**需要回忆其后台字段定义、使用位置以及如何关联游戏、渠道或日志。

**追问**：堆栈最上层在渠道 SDK，能判定 SDK 有错吗？

不能。异常暴露位置不必然等于根因；宿主传错参数、生命周期不匹配、依赖版本不一致都可能在 SDK 内表现出来。应结合前置条件和调用链验证，而非根据包名定责。

<a id="q-i17"></a>
### I17｜怎么证明修复有效，而不是“测一下不崩就发”？

**参考回答**：“我会区分原问题复现、修复后验证、相关链路回归和发布后观察。修复前应该有可重复的失败条件；修复后用相同条件验证，再覆盖受影响渠道和业务流程。发布后还要看同类异常是否继续出现，而不是只看汇总指标。”

**继续追问**：为什么总崩溃率下降，还可能没修好？

因为用户与版本构成、活跃量和场景分布可能变化；具体崩溃仍在，只是被更大的分母稀释。反过来，总体上涨也不必然说明这次修复失效，应看同版本、同问题和相近样本。

**事实边界**：简历有修复协作、回归和版本验证；灰度、自动化回归平台、监控告警、回滚机制是否参与，仍需本人确认，不补写成既成经历。

<a id="q-i18"></a>
### I18｜转化率看板有什么用？哪些指标可以算你的成果？

**参考回答**：“转化率需要先明确漏斗，例如初始化到登录、拉起支付到某种支付结果。看板异常只能提示某一环节可能变化，需结合错误码、渠道及版本分布和日志进一步定位。接口改动或埋点口径变化本身也可能造成指标变化。”

**追问**：你提高过多少转化率？

没有确认的前后对比，不写提升百分比。可以讲“利用看板缩小排查范围，结合日志完成定位并协同验证”，但具体是哪一次问题、你提交了什么修改，需要真实案例支撑。

**个人成果表达原则**：动作可归个人，例如编写工具、定位调用链、修改依赖；整体指标描述为“维护期间观察到的整体结果”；有基线、统一口径和对照后，才讨论变化及自己的贡献，避免把相关性当因果关系。

### 本章面试前补证清单

- [ ] 找出最熟悉的一个渠道与具体 SDK 版本，确认自己真正修改的模块。
- [ ] AndroidX 案例补齐一个准确报错、两条冲突来源及最终修改项。
- [ ] 确认是否使用过 Jetifier、依赖排除、版本约束或其他方式；未用过只讲原理。
- [ ] 明确检测到的设备标识和敏感 API，调用时机、频次统计方式与复现步骤。
- [ ] 区分工具已实现功能与理想功能：堆栈、自动化场景、报告、native、多进程分别是否支持。
- [ ] 补齐隐私问题实际由谁修、改了什么、你负责什么、如何验证、最后状态。
- [ ] 核实 0.25% 的分子、分母、统计周期、平台及归因范围；无法核实则弱化或删数值。
- [ ] 查清 pid/gid 的公司内真实含义，并准备脱敏的关联排查示例。
- [ ] 准备一条完整的“告警/反馈 → 日志 → 原因 → 修改 → 回归 → 版本验证”故事。
- [ ] 若旧版简历的 Objective-C SDK 或 Swift 下载工具仍会被问到，先核实它们是否还在投递版本；没写进当前简历也不必主动扩充为本次主线。

### 三条最容易失分的说法

1. **“我把 Android 升级成了 AndroidX。”** → 改成“推进工程及依赖的 AndroidX 迁移”。
2. **“我把崩溃率降低到了 0.25%。”** → 改成“维护期间整体 SDK 崩溃率低于 0.25%，具体口径待核实”；无可信口径就去掉数字。
3. **“频繁取设备 ID 一定违法，我用缓存彻底解决了。”** → 改成“上线前发现并定位频繁访问风险”；根因、修复和最终结论分别按真实记录表述。

## 练习与材料准备

### 七次练习安排

每次练习以能脱稿回答为目标，不以读完页数为目标；时间紧时先完成前四次。

1. **项目全貌与贡献边界**：录制自我介绍和 SSH Mobile 的 90 秒介绍；明确自己设计、修改、审查、调试过的代码，准备一张模块关系草图。
2. **Rust SDK 与异步生命周期**：从 Flutter 发命令讲到原生结果返回，解释内存所有权、请求关联、超时、取消、dispose 与迟到结果。
3. **网络传输与故障恢复**：分别演练连接中断、文件接收完成但 ACK 丢失、校验失败、消费者过慢四种场景。
4. **真实实习案例**：补全一个 AndroidX 冲突案例、一条设备标识访问检测链路，以及 0.25% 看板口径；找不到的事实明确留空。
5. **Compose 与 Flow**：画出刷新、点赞、发布的状态变化；解释 StateFlow、SharedFlow、生命周期与缓存回退。
6. **Agent 与性能**：画出模型调用与工具审批循环，讲清冷启动、首次功能加载及没有实测数据时的表达边界。
7. **模拟面试**：每个问题先答结论，再讲实现，再接受两层追问；将答不清的点回到代码和官方文档核对。

### 建议自己写的 8 个小练习

这些是练习题，不代表简历项目已经实现了全部策略。

- 写一个并发请求共用同一初始化 Future 的 single-flight，验证失败后能重试、销毁后不发布资源。
- 写一个 commandId 到 pending 请求的映射，处理成功、超时、重复响应和 dispose。
- 用容量有限的队列连接快生产者和慢消费者，观察积压、背压及取消传播。
- 写一个流式文件复制，加入取消、进度、哈希校验及临时文件清理，观察业务层内存是否随文件大小增长。
- 用 Kotlin StateFlow 更新点赞状态，模拟两个并发修改并观察非原子读改写的问题。
- 分别在 SharedFlow 的无订阅者、有订阅者、生命周期暂停和恢复时发送事件，记录实际行为。
- 用 fake Repository 测试刷新网络失败时的有缓存、无缓存及损坏缓存三种情况。
- 构造审批后目标服务器变化的测试，验证目标失效时不会执行操作；同时解释这与远端文件变化的区别。

### 面试随身准备的证据清单

| 主题 | 最低限度可展示或口述的证据 | 不能替代它的内容 |
| --- | --- | --- |
| 个人贡献 | 自己能解释的一条变更、一个调试过程、一个设计取舍 | 仅展示整个仓库代码量 |
| 冷启动 | 前后初始化调用顺序、按需资源与首次使用代价 | 900 ms 定时器被删除 |
| 大文件 | 整文件预加载到分块读写的变更、取消清理路径 | 块大小直接当峰值内存 |
| 可靠传输 | 中断恢复与完成确认流程、失败场景 | 只说使用 QUIC |
| Agent | 模型 API、客户端循环、审批与工具执行的边界 | 只说用了大模型 |
| Compose | 真实 ViewModel、流配置、收集位置、缓存分支 | 通用架构图 |
| SDK 兼容 | 一条真实报错、依赖路径、修改与验证 | “解决了各种冲突” |
| 隐私检测 | API、调用时机、调用次数的统计方式与模块归因 | 笼统断言违法或已彻底解决 |
| 崩溃率 | 分母、去重方式、周期、SDK 归因与版本范围 | 不可解释的 0.25% |

### 不知道时如何回答

不要用一大段术语掩盖不确定。可以按下面的顺序说：

1. “这个点我实际做到了……，我能说明这部分实现。”
2. “对于你问的……场景，目前没有专项验证／我需要核对当时记录。”
3. “如果继续排查，我会先观察……，再用……方式验证这个假设。”

例如：“我实现过按需初始化和 Isolate 下沉，但没有保留可复核的冷启动对比数字。我会固定设备、构建模式和数据条件，对第一帧、可交互以及首次功能加载分别测量，而不是现在估一个提升比例。”

### 最后提醒

这份手册覆盖简历中的技术术语及其主要追问，但不可能穷尽所有面试题。核心目标是让你的每一句简历描述都能落到具体代码、真实职责和可验证的边界。面试前还应单独练习编码题，并确认可实习时间、每周到岗天数与预计毕业时间。
