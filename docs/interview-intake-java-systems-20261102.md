## 语言、并发与模式

<a id="js01"></a>
### JS01 P0 自定义注解为什么选 RUNTIME，SOURCE 和 CLASS 有何差别

**口述回答：** 按注解的消费者选择保留策略。只给源码检查或编译期处理器使用，可选 SOURCE；需要保留到编译产物、供后续字节码工具分析，可选 CLASS；程序运行时需要反射读取，才选 RUNTIME。Java 注解没有显式声明 `@Retention` 时默认 CLASS。不是选得越久越好，也不是加一个 RUNTIME 就会自动执行注解代表的功能。

**原理与边界：** 注解是元数据，真正行为由编译器、处理器、构建工具或运行时读取逻辑实现。Java 的保留策略不能直接照搬为 Kotlin 默认值；还应核对 `@Target`、属性对应的使用点目标和混淆后的读取方式。

**追问：** 编译期生成注册代码必须 RUNTIME 吗？ **答：** 不必须；处理器在编译期就能消费注解，生成代码之后可以不再依赖运行时注解。

**追问：** 反射为什么读不到 CLASS 注解？ **答：** CLASS 只承诺记录到 class 文件，不要求虚拟机在运行时保留并暴露给反射。

**易错点：** 把保留策略称为 Android 生命周期；或声称 RUNTIME 注解一定导致明显性能问题，而没有测量读取方式和调用频率。

**官方参考：** [RetentionPolicy](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/annotation/RetentionPolicy.html)。

<a id="js02"></a>
### JS02 P0 双重检查单例为什么检查两次，volatile 解决什么

**口述回答：** 第一次检查让实例建立后的常见路径避开同步；进入同一把锁后再次检查，防止先后获得锁的线程重复创建。共享实例引用还要正确发布，典型 Java DCL 使用 volatile，使读取线程能够看到构造完成的状态。这里是“两次判断、一把锁”，不是两把锁。简单场景也可以用静态初始化、静态内部类持有者或枚举，先看创建时机和依赖再选择。

**原理与边界：** volatile 解决发布与可见性关系，不使单例内部的所有可变字段自动线程安全。类初始化方案依赖运行时的初始化同步规则；“单例”通常也受进程和 ClassLoader 边界限制，不是多进程唯一。已有 [Q050](../questions/08-并发与线程安全/Q050-线程安全单例怎样正确实现.md) 是基本写法入口。

**追问：** 全局变量就是单例模式吗？ **答：** 全局可达描述访问范围，单例模式还约束实例创建与提供访问入口；公开一个可变引用并不能阻止其他地方 new，也不自动解决依赖与测试隔离。

**追问：** Kotlin `object` 能代替所有单例吗？ **答：** 能表达特定运行时边界内的单实例，但带参数配置、资源释放、依赖替换与多进程仍需单独设计。

**易错点：** 只背“禁止指令重排”却无法说明哪个写入和哪个读取建立关系；持有 Activity 的单例还可能造成泄漏。

**官方参考：** [JLS 17.4.5 happens-before](https://docs.oracle.com/javase/specs/jls/se17/html/jls-17.html#jls-17.4.5)、[JLS 12.4.2 类初始化](https://docs.oracle.com/javase/specs/jls/se17/html/jls-12.html#jls-12.4.2)。

<a id="js03"></a>
### JS03 P0 新增上传方式怎样体现开闭原则和里氏替换

**口述回答：** 先为上传定义稳定契约，例如输入来源、进度、取消、错误和“完成”的含义，再让调用方依赖 `Uploader` 抽象。新增 HTTP、SFTP 等实现主要增加实现类并在组装处注册；旧业务无需到处增加协议分支，这是对可预期变化的开放扩展。里氏替换要求新实现遵守原契约，不能把“任务入队成功”伪装成“文件已保存成功”，也不能突然要求调用方先做额外初始化。

**原理与边界：** 开闭原则不等于一个旧文件都不允许修改，也不要求一开始就支持任意未来协议。某协议不支持断点恢复时，应声明能力、返回明确结果或拆分接口，而不是用空实现满足方法签名。这里是设计练习；SSH Mobile 的实际完成阶段继续以其源码导读为准。

**追问：** 工厂和适配器在这里做什么？ **答：** 工厂集中创建和选择上传实现；适配器把第三方 SDK 的不同签名与回调转换为自有契约。它们不能掩盖协议本身不支持的能力。

**追问：** 如何证明可替换？ **答：** 给全部实现运行同一组契约测试，覆盖空文件、取消、超时、重复调用和完成含义，再补每个协议的专属测试。

**易错点：** 只写了一个 interface 就宣布满足里氏替换；或为了“不改旧代码”引入无必要的插件框架。

**官方与原始参考：** [Microsoft：依赖反转与封装](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/architectural-principles)、[Liskov 与 Wing：行为子类型原论文](https://www.cs.cmu.edu/~wing/publications/LiskovWing94.pdf)。上传案例是根据这些原则推导的练习。

<a id="js04"></a>
### JS04 P0 观察者、责任链、模板、工厂与适配器分别解决什么

**口述回答：** 观察者让事件源通知多个订阅者，例如播放器状态通知页面与通知栏；责任链让多个处理环节依次处理或转交，例如日志、认证和重试拦截器；模板方法固定算法骨架，把某些步骤交给子类；工厂集中创建对象；适配器转换接口。例如同一音频缓存接口下，工厂选择实现，适配器包住第三方下载器。应先讲变化点和协作关系，再说模式名。

**原理与边界：** 这些模式不是互斥选项，也不是见到监听回调就已经解决了线程、顺序、丢事件与泄漏。Flow 有可观察数据流的一面，但冷流按收集启动、热流共享、背压及取消等语义，不能仅用“观察者模式”概括。Java 旧 `Observable` 已弃用，不应因为讲模式就推荐它。

**追问：** 观察者有哪些隐藏问题？ **答：** 需要定义回调线程、订阅与退订所有者、事件顺序、重入、慢消费者和错误隔离；页面销毁后还被全局事件源持有是典型泄漏。

**追问：** 模板与责任链如何区分？ **答：** 模板在一个固定控制流程内替换步骤；责任链由独立节点协作并决定是否继续。OkHttp 的 proceed 还允许回程处理响应，不只是“所有节点都调用一次”。

**易错点：** 把任何方法调用列表称为责任链；把 Java `Object.wait/notify` 和观察者通知混为一谈。

**官方参考：** [Java Observable 的弃用与通知边界](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Observable.html)、[OkHttp 仓库维护的 Interceptors 文档](https://raw.githubusercontent.com/square/okhttp/master/docs/features/interceptors.md)。后者是可变分支，需按实际依赖版本核对；模式归类是对协作机制的解释，不表示个人已实现对应功能。

<a id="js05"></a>
### JS05 P0 让多个线程按顺序执行，应该先澄清哪一种顺序

**口述回答：** 区分提交顺序、开始顺序、同步任务返回顺序，以及网络或设备真正完成的顺序。A 完成后才做 B，可在线程外按依赖组织任务，或用 join、Future、Latch 等建立完成关系；如果任务本身只启动异步操作就返回，单线程队列也不能保证业务完成顺序。失败、取消和超时必须能终止后续依赖，不能靠 sleep 猜测。

**原理与边界：** CountDownLatch 是一次性计数门闩；`countDown` 前的动作与对应 `await` 成功返回后的动作有 happens-before 关系。它不携带业务成功结果。若失败时不释放门闩可能永久等待；若 finally 总是释放而未记录失败，下游又可能错把失败当成功。

**追问：** 三个任务必须用三条线程吗？ **答：** 不必须；同步短任务在单条工作线程顺序执行更简单。真正存在并行或线程亲和要求时再引入同步设施，Android 主线程不能阻塞等待。

**追问：** synchronized 能保证 A、B、C 次序吗？ **答：** 互斥不等于指定顺序；竞争获得锁的先后没有这种业务承诺，必须有条件谓词或依赖关系。

**易错点：** 主线程 join；用无超时等待掩盖失败；任务线程占满线程池后还等待同池里排队的后续任务。

**官方参考：** [CountDownLatch：等待与内存一致性](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/CountDownLatch.html)。

<a id="js06"></a>
### JS06 P0 Java 基本类型的位宽，是否等于对象占用字节数

**口述回答：** Java 的 byte、short、int、long 分别为 8、16、32、64 位有符号整数；char 是 16 位无符号 UTF-16 代码单元；float、double 对应 32、64 位浮点格式；boolean 只有 true/false 的语言语义，不能据此宣称每个布尔变量总占固定一个字节。装箱对象、数组和字段还受对象头、对齐与运行时实现影响。

**原理与边界：** 位宽规定表示范围，不直接等于整个对象的内存。char 不一定表示一个完整 Unicode 字符：补充平面的码点需要一对代理代码单元。Java 引用也不能随口说成 4 字节或 8 字节，需看运行时配置与具体表示。

**追问：** `public static` 能保证线程安全吗？ **答：** public 控制可访问性，static 表示类级成员，二者都不提供同步。实例 synchronized 方法锁接收对象，静态 synchronized 方法锁对应 Class 对象；多个调用必须用同一同步约定。

**追问：** `int` 不会撕裂，所以自增就安全吗？ **答：** 自增包含读改写，仍可能丢更新；单次读写的原子性不等于整个复合操作原子性。

**易错点：** 把语言范围、对象大小、编码长度和网络序列化格式当成同一问题。

**官方参考：** [JLS 4.2 基本类型](https://docs.oracle.com/javase/specs/jls/se17/html/jls-4.html#jls-4.2)、[JLS 8.4.3 方法修饰符](https://docs.oracle.com/javase/specs/jls/se17/html/jls-8.html#jls-8.4.3)。

## 系统与语言边界

<a id="js07"></a>
### JS07 P1 虚拟内存、堆栈与线程切换为什么不能混在一起讲

**口述回答：** 虚拟内存给进程提供地址空间、映射和保护，页表把虚拟地址关联到物理页等后备资源；不是简单“用磁盘扩大 RAM”。堆、线程栈、共享库映射等是地址空间中的不同用途。线程切换需要保存和恢复执行上下文，例如寄存器、栈指针和恢复位置；跨地址空间还可能涉及映射切换及 TLB/cache 影响，成本取决于平台，不能一概给固定倍数。

**原理与边界：** Java 栈帧、Java 堆是运行时抽象，不可机械等同 C/C++ 所有对象的存储方式；C++ 还区分自动、静态、动态等存储期。所谓“C 的调用堆/调用栈哪个快”应先澄清是在问分配、函数调用还是访问，不能给“Java 慢因为有虚拟机”的万能答案。

**追问：** 线程切换具体是哪条指令？ **答：** 不能脱离 CPU 架构、内核版本及切换路径作答；ARM64 与 x86 实现不同，也不是一条通用 Java 指令完成。先解释需要保存什么，再定位目标内核的架构实现。

**追问：** 进程崩溃一定不影响其他进程吗？ **答：** 地址保护通常隔离普通用户态错误，但共享资源、关键服务退出、依赖链与系统级故障仍可能产生连带影响。

**易错点：** 认为每次切换都复制整个堆；或把缺页全部解释为必须从磁盘读取。

**官方参考：** [Linux 内存管理概念](https://docs.kernel.org/mm/concepts.html)、[Linux ARM64 entry.S 源码](https://github.com/torvalds/linux/blob/master/arch/arm64/kernel/entry.S)。动态源码仅作定位入口，不保证与某台 Android 设备版本一致。

<a id="js08"></a>
### JS08 P1 C++ 指针和引用怎么区分，引用为什么也可能悬空

**口述回答：** 指针对象存放地址，可以为空、重新指向和参与受规则约束的算术；引用在初始化时绑定对象，之后赋值通常修改被引用对象，而不是重绑定。引用适合表达必须有对象的参数契约，但不会自动延长任意对象生命周期，也不是内存安全保证。返回局部对象的引用、对象销毁后继续使用引用都会出问题。

**原理与边界：** 引用在语义上是别名，不能承诺底层永远不占空间或总比指针快。`const T&` 表示经该引用不能直接修改对象，不代表其他别名无法修改。所有权应另外表达，例如 `unique_ptr`、`shared_ptr` 或明确借用契约。

**追问：** `T*&` 是什么？ **答：** 指向 T 的指针的引用，可通过它修改调用者持有的指针本身；与把指针按值传入不同。

**追问：** Kotlin/Java 引用能照搬 C++ 引用规则吗？ **答：** 不能；Java 参数仍按值传递，复制的是引用值，生命周期又由不同运行时机制管理。

**易错点：** “引用不能为空，所以引用绝不可能非法”；或为省拷贝返回已销毁局部变量的引用。

**原始参考：** [ISO C++ FAQ：References](https://isocpp.org/wiki/faq/references)。

<a id="js09"></a>
### JS09 P1 Linux 看 CPU 和内存时，应该先看什么指标

**口述回答：** 先固定观测时段与进程，再用 top 查看 CPU、线程及资源变化，用 `/proc` 查看系统和进程指标；需要分清虚拟地址规模、常驻物理页及共享页，不能把 VSZ/VIRT 当成真实独占内存。Android 还可结合 dumpsys meminfo、Profiler 与 traces，看 Java/native、图形和映射等不同部分。单张截图不够判断泄漏或 CPU 热点。

**原理与边界：** `/proc/meminfo` 的 MemAvailable 是可用内存估算，free 低不必然代表压力；top 的 CPU 百分比也需说明多核计数方式与刷新窗口。连续增长、GC 后保留、页面退出后仍有引用，才是进一步分析线索。命令选项随 procps/Android toybox 版本不同。

**追问：** 日志中某进程 150% CPU，是错了吗？ **答：** 某些显示模式按单核 100% 计，多个线程并行可以超过 100%；先核对工具的归一化方式。

**追问：** RSS 增长就证明 Java 泄漏吗？ **答：** 不能；还可能是 native、图片峰值、映射或缓存，需要堆转储、引用链及负载对照继续判断。

**易错点：** 为了“验证性能”在生产服务器随意跑压测；或混用系统总内存、单进程 RSS 和 Java 堆大小。

**官方/维护者参考：** [Linux proc 文件系统](https://docs.kernel.org/filesystems/proc.html)、[procps top 手册](https://man7.org/linux/man-pages/man1/top.1.html)。本题未在用户服务器执行命令。

## 缓存、安全与工程证据

<a id="js10"></a>
### JS10 P0 密码为什么加盐，为什么不能把 MD5 叫加密

**口述回答：** 哈希将输入映射为摘要，不是可逆加密。MD5 已不适合需要抗碰撞的安全用途，且速度快，对低熵密码尤其容易离线猜测。服务端应采用适合密码存储、可调整成本的口令哈希方案，给每个密码设置独立随机盐，记录算法、参数、盐和结果；验证时按同一参数计算并安全比较。盐通常无需保密，但必须防止不同密码记录简单共用预计算成果。

**原理与边界：** 例如选用成熟库实现的 Argon2id（RFC 9106），按服务端内存、计算资源与验证延迟预算选择参数，记录版本并支持之后升级；不是自己组合摘要算法。盐不提高用户密码自身的熵，也不阻止攻击者对某个账户逐个猜测。密码派生、普通摘要、消息认证与传输加密解决不同问题；只换成一次 SHA-256 仍未解决“快”的问题。不要在客户端存可恢复的登录密码，也不要在日志记录密码。

**追问：** 碰撞与找回原密码是同一攻击吗？ **答：** 不是。碰撞寻找任意不同输入的同摘要，原像攻击针对给定摘要寻找输入；密码破解还利用人类密码分布和大量猜测，不能只背“MD5 有碰撞”。

**追问：** 密码加盐后还需要 HTTPS 吗？ **答：** 需要；存储防护不能替代传输中的身份验证、机密性与完整性。

**易错点：** 自己拼“多次 MD5+固定盐”当作现代密码存储；声称服务器必须把盐藏起来才能验证。

**官方参考：** [NIST SP 800-63B：密码验证器](https://pages.nist.gov/800-63-4/sp800-63b.html)、[RFC 6151：MD5 安全边界](https://www.rfc-editor.org/rfc/rfc6151)、[RFC 9106：Argon2id 与参数选择](https://www.rfc-editor.org/rfc/rfc9106)。

<a id="js11"></a>
### JS11 P1 缓存击穿如何用逻辑过期处理，代价是什么

**口述回答：** 为缓存值增加业务过期时间。过期时先判断是否允许返回旧值；允许时返回可接受的旧数据，并让一个重建者异步刷新，其他请求避免同时打数据库。它以一定陈旧度换可用性，适合能容忍旧值的热点读；库存扣减、支付状态等强一致决策不能直接套用。物理 TTL 与逻辑过期不同，底层键被淘汰或真的失效时仍需要回源策略。

**原理与边界：** 逻辑过期是应用层方案，Redis 并没有一个替你保证全流程正确的“逻辑过期锁”。重建需限并发、失败退避和有界旧值期限。跨进程互斥还涉及锁租约、持有者身份、超时后的迟到写与版本控制，不能只写一个 setnx 就宣称绝不并发。

**追问：** 与缓存穿透、雪崩有何区别？ **答：** 击穿是热点失效导致并发回源；穿透是大量查询不存在的数据；雪崩通常是大范围失效或缓存整体不可用。故障表现可能叠加，但措施不同。

**追问：** 锁过期后老重建结果覆盖新值怎么办？ **答：** 用数据版本或条件写防止过期持有者写回；仅“解锁时比较 token”不能阻止已经失效的业务写入。

**易错点：** 无限返回旧值；把逻辑过期写成 Redis 官方保证的强一致算法。

**官方参考：** [Redis SET 的条件与过期参数](https://redis.io/docs/latest/commands/set/)、[Redis 分布式锁与有效期边界](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。本题缓存流程为编辑者基于这些机制推导的方案。

<a id="js12"></a>
### JS12 P1 Redis 防重复消费为什么不等于业务只执行一次

**口述回答：** 先定义业务幂等键和成功状态，再看“认领消息”和“提交业务副作用”是否能原子完成。Redis 的条件写可以帮助短期去重，但进程在写标记后、业务提交前崩溃，会漏执行；先提交业务再写标记，又可能重复。对于数据库业务，常用唯一约束与业务更新放进同一事务；外部支付或设备动作还需要对方的幂等协议、持久状态和对账恢复。

**原理与边界：** 本地内存只覆盖当前进程且重启丢失；数据库约束便于和业务事务一致；Redis 可提供跨实例的快速共享状态，但有过期、淘汰、持久化和故障切换边界。选择取决于容错与吞吐要求，而非“Redis 比数据库快”一句话。不要把锁、去重和 exactly-once 混用。

**数据类型速答：** 常见 String 可表达字节串、计数或条件认领；Hash 表达字段集合；List 表达有序序列；Set 表达无重复成员；Sorted Set 为成员维护分值排序。Streams 还支持流式记录与消费组。Bitmap/HyperLogLog 等有不同能力和精度边界；这不是“Redis 只有五种类型”的完整清单，具体可用类型与命令需核对部署版本。List 或消费组也不自动把外部业务副作用变成 exactly-once。

**追问：** SET NX 成功后一直不删就安全吗？ **答：** 不安全；还要区分处理中、已完成、失败可重试和处理超时，并考虑标记丢失或过期。永久标记也不能补回未提交的业务。

**追问：** 重复请求内容变了但幂等键相同怎么办？ **答：** 校验请求摘要和身份范围，明确返回冲突；不能把不同操作静默当作同一结果。

**易错点：** 宣称仅靠 Redis 实现任何业务“零重复、零丢失”；给所有错误统一重试却不确认副作用。

**官方参考：** [Redis SET](https://redis.io/docs/latest/commands/set/)、[Redis 数据类型](https://redis.io/docs/latest/develop/data-types/)、[PostgreSQL 唯一约束](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)。数据库例子不表示用户项目采用 PostgreSQL。

<a id="js13"></a>
### JS13 P1 短链接、布隆过滤器与数据库写失败如何形成完整方案

**口述回答：** 先明确短码生成、唯一约束、过期与跳转规则，再看缓存和布隆过滤器是否必要。布隆过滤器可对“可能存在”做紧凑预筛；在正确维护、无遗漏的前提下，否定结果可拒绝无效查询，肯定结果仍需查缓存或数据库。短码碰撞要由唯一约束兜底并有限重试，不能因为摘要不同概率很低就忽略冲突。

**原理与边界：** 过滤器可能误报，不能提供短码唯一性，也不能作为唯一数据库。新建记录尚未同步到过滤器时会出现业务上的漏查，所以必须设计写入顺序、失败补偿、重建及旁路策略；理论“不漏报”有维护前提。数据库写失败时不能提前发布一个无法查询的短码，重试也需保证请求幂等。

**追问：** 能删除位数组里的一位吗？ **答：** 普通布隆过滤器的位被多个键共享，随意清零会导致漏报；需要支持删除的方案或按周期重建。

**追问：** 为什么不用本地 Set？ **答：** 数据量小时可能更简单；多实例一致、重启恢复、内存预算和同步成本才是取舍依据，不是工具越复杂越好。

**易错点：** “布隆判断存在就直接跳转”；把面经作者的短链、秒杀或论文实现说成自己的项目。

**官方参考：** [Redis Bloom filter](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)、[PostgreSQL 唯一约束](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)。

<a id="js14"></a>
### JS14 P1 面试问 QPS、云 Redis 性能和压测结果，怎样给可复核答案

**口述回答：** 没测过先如实说明，再给实验方案：固定硬件、网络拓扑、版本、数据规模、命中率、读写比例和连接配置，区分预热与正式采样；同时记录吞吐、p50/p95/p99、错误率和资源占用。要区分 Redis 单命令吞吐、某接口端到端吞吐与手机页面性能，它们不是同一指标。客户端和服务器跨网络时，RTT、连接复用与批处理会显著改变结果。

**原理与边界：** 闭环并发数固定的压测可能因服务变慢而自动减少发压，不能仅看平均耗时。流水线吞吐高不等于单请求延迟低；缓存全命中结果不代表数据库回源表现。压测只能在隔离且获授权的环境进行，不能用用户现有在线服务作随意实验。

**追问：** 用上 Redis 就一定比数据库快吗？ **答：** 不一定；小负载、额外网络跳数、序列化和低命中率可能抵消收益，需要按目标工作负载对照。

**追问：** 面试官要数字但你忘了怎么办？ **答：** 说明当时记录缺失，讲清优化前后机制和仍有证据的验证，不临场编数字；未来补测也应标明新的测试时间与条件。

**易错点：** 把网络工具或组件 benchmark 的结果写成个人业务系统 QPS；用一个请求的耗时宣布 p99。

**官方参考：** [Redis Benchmark：测试方法与常见误区](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/)。

<a id="js15"></a>
### JS15 P1 逆向、证书校验和 Hook 面试题如何在自有实验 App 中验证

**口述回答：** 先限定授权范围，再区分静态分析与动态插桩。静态分析看编译产物、资源和调用关系，不能还原全部源码语义；动态插桩观察运行时方法、参数和调用栈。Frida 提供进程内动态插桩及 Java/native API；Xposed 通过其 Android 运行时框架加载模块并拦截方法，部署前提和版本兼容不同。工具名不等于掌握，应能解释自己实际观察过的路径与局限。

**原理与边界：** 面经里的“第三方证书破解”不作为练习步骤。对自己的 debug App，应通过 Network Security Configuration 等显式测试配置接入测试 CA，验证错误主机名、不受信任证书和过期证书确实失败；release 不得携带宽松测试配置。TLS 校验、证书固定、应用完整性和设备 root 状态是不同问题。

**追问：** 自有 App 的一次 Hook 实验应记录什么？ **答：** 固定版本与测试设备，选择自编的无敏感数据方法，观察调用前后和栈，记录正确重载/线程及资源释放；最后关闭插桩对照结果，不给第三方账户或应用做绕过。

**追问：** 看不到某次 Java 方法就能证明它没执行吗？ **答：** 不能；可能选错进程、ClassLoader、重载、时机，或路径位于 native，需与日志及源码交叉验证。

**易错点：** 把“信任所有证书”当作解决线上 HTTPS 问题；把成功打印日志说成已完成隐私合规审计。

**官方/项目原始参考：** [Frida JavaScript API](https://frida.re/docs/javascript-api/)、[Xposed 项目开发说明](https://github.com/rovo89/XposedBridge/wiki/Development-tutorial)、[Android Network Security Configuration](https://developer.android.com/privacy-and-security/security-config)。

### JS16 P0 共享屏幕讲源码、AI 开发与未知业务追问，如何准备而不编经历

**口述回答：** 准备“入口—状态所有者—业务调用—存储或网络—结果回传—失败清理”一条真实调用链，每个包解释职责及依赖方向。选择一项自己能修改并验证的功能做现场演示，保留离线样例与失效提示；不能把第三方接口临时不可用伪装成项目从未有问题。AI 辅助部分说明实际目标、生成内容、人工取舍、发现的错误和验证证据，不把提交数量当个人理解证明。

**原理与边界：** 秒杀、短链、论文、新闻 App、环境音量算法等是其他原作者的背景。没有对应实现就给准备框架：需求与约束、数据流、正确性风险、取舍、验证、未完成部分。算法团队协作只讲实际接口与实验，不自称设计了未参与的算法。新 Flutter/老 Java 迁移、RN 改 H5及移动端前景是取舍/观点题，应先问团队约束，不能编唯一标准答案。

**追问：** 怎么解释 git merge？ **答：** 它把指定历史合入当前分支；可快进时移动分支指针，分叉时通常需要三方合并并产生合并提交，也可能发生冲突。解决文本冲突之后还要运行相应验证，不能把“Git 没报错”当作行为正确。

**追问：** AI 生成实现和测试都通过还可能有什么问题？ **答：** 二者可能共享错误假设；要按独立需求构造反例、检查边界及真实依赖。不能以 AI 审查替代人工理解、安全和集成验证。

**易错点：** 背“我做了高并发秒杀”而实际没有；只记包名不知一条请求经过哪里；把新补做的实验倒写成当初经历。

**官方参考：** [git merge](https://git-scm.com/docs/git-merge)、[GitHub：Agent 局限与人工审查](https://docs.github.com/en/copilot/responsible-use/agents)。个人接管练习见 [AI 辅助代码接管练习册](ai-code-takeover-workbook.md)。

<a id="js17"></a>
### JS17 P1 CPU 调度算法怎么比较，Android 能否只背时间片轮转

**口述回答：** 先说目标：吞吐、响应时间、公平性、优先级与实时约束可能冲突。先来先服务简单但长任务会拖慢后续，短作业优先依赖对运行时长的估计且可能饿死长任务，时间片轮转让可运行任务轮流获得机会。实际 Linux 调度按线程、调度类别及策略工作，普通任务和实时策略不能混成一种算法；Android 还受内核版本、设备厂商、分组和 CPU 性能策略影响。

**原理与边界：** Linux 普通任务的公平调度实现随版本演进，已有向 EEVDF 过渡的实现，不能宣称所有当前设备都只用老 CFS 或简单轮转。SCHED_FIFO、SCHED_RR 等实时策略有不同规则。这里讲机制与阅读入口，不表示普通 App 可以任意提升到实时优先级。

**追问：** 线程优先级高，就一定先完成吗？ **答：** 不一定；任务可能在等待锁或 IO，也受可运行状态、CPU 亲和性与其他策略限制。优先级不是业务顺序协议。

**追问：** 时间片越小越好吗？ **答：** 小时间片可能改善部分响应，但会增加切换和缓存影响；过大又会损害延迟，需要按负载和调度目标权衡。

**易错点：** 用 Java `Thread.start()` 的调用顺序推导 CPU 执行顺序；或把 SCHED_RR 误说成所有 Android 线程的默认策略。

**官方/维护者参考：** [Linux EEVDF 文档](https://docs.kernel.org/scheduler/sched-eevdf.html)、[Linux sched(7) 策略接口](https://man7.org/linux/man-pages/man7/sched.7.html)。sched(7) 对默认 CFS 的历史描述不能替代目标内核版本核对。
