# SSH Mobile AI 辅助代码接管练习册

这份练习册与源码导读配套使用。原手册的 129 题用于查概念，这里用于验证你是否能定位、解释、修改和测试实际代码。**以下全部是建议开展的新练习，不是已完成测试、历史个人贡献或现有实现保证。** 源码位置以配套导读锁定的提交为准，练习时记录自己的提交号，避免把后来改动当成历史事实。

最值得先交付的成果是：一份真实贡献表、一条能脱稿画出的调用链、两个自己完成的故障验证记录。没有必要先把项目全部重写，也不要急于把每一个高级术语都变成简历卖点。

## 一 先分清项目能力和个人能力

### 贡献与理解程度模板

- 需求最初由谁提出，我做了哪些选择：________
- AI 生成或建议的部分：________
- 我亲手修改的部分及原因：________

- 我亲自执行过的测试、日期和结果：________

- 仍未理解或未验证的边界：________
- 对外可展示的脱敏证据：________

| 掌握等级 | 可观察标准 | 面试中的使用方式 |
| --- | --- | --- |
| A 可以接管 | 不看答案能定位关键代码，解释失败路径，完成一个小改动并验证 | 可以作为重点，但仍须准确归属历史工作 |
| B 能够解释 | 能说明调用链和取舍，尚未独立改动或验证关键边界 | 讲项目现状，不宣称独立设计并解决全部问题 |
| C 知道用途 | 能说出模块作用，不能展开实现和故障处理 | 不作为核心卖点，明确仍在学习 |

**等级是当前掌握程度，不是历史贡献证明。** 现在补做练习可以把 C 提升为 A，但不能因此说最初就是你独立实现的。提交记录和代码量同样不能证明个人理解深度。

### 面试表达模板

以下括号必须替换成真实事实；不能把未发生的动作补成顺口的故事。

> 这个项目大量使用了 AI 辅助生成代码。我会区分项目已具备的能力和我本人实际负责、掌握的部分。我实际做过的是【真实动作】，目前能独立展开的是【具体模块】。例如【有证据的修改或验证】。底层 QUIC、Tokio 等能力依赖成熟库，项目做的是【经源码确认的 SDK 封装与业务编排】；【尚未理解的部分】我还没有完整验证。

被问到“这不是 AI 写的吗”时，不需要回避，也不必只回答“是”。继续给出可核查的具体内容：

> 是，AI 参与了代码生成。【这段代码】最初主要由 AI 生成。我现在能解释【入口、状态和失败路径】，并在【日期】亲自补做了【验证】。关于【未知边界】，我还没有足够证据，不会说已经解决。

没有做过调试案例时，直接说尚未做过。先完成下面的练习，再用真实结果更新表述，不要从练习题倒推一段虚构经历。

## 二 四条从入门到进阶的实践路线

每条路线都按“读懂正常路径 → 控制一个失败 → 独立做小改动 → 解释边界”推进。完成一条再展开下一条，比同时背四套术语更有效。

### 路线一 Flutter 到 Rust SDK

**入门：追一条真实命令。** 从一个按钮或业务方法开始，沿源码标注 Dart 请求、序列化、FFI 入口、Rust 解码/派发、异步执行、事件队列、poll、Dart 解码与 UI 更新。不要预设每个模块都经过完全相同的路径；以该命令实际代码为准。

每一步回答五件事：输入是什么、谁调用、当前在哪个执行环境、成功意味着什么、错误交给谁。把 UI Isolate、工作 Isolate、原生同步调用和 Tokio 任务分别画出来，不把 `await` 自动画成“切线程”。

**基础：列一张资源表。** 对本条链路出现的句柄、字节缓冲、文件、订阅逐项写清创建者、所有者、有效期、释放方法。重点查编码是否复制数据，原生返回的内存何时失效，错误分支是否也释放。不要靠变量名猜所有权，也不要为了练习故意在真实 FFI 中访问已释放指针。

**进阶：实现一个教学版 pending 管理器。** 用 fake transport 和可控时钟，不接真实服务器。覆盖成功、拒绝入队、超时、重复事件、迟到事件及 dispose。它的用途是训练状态机，不是要求替换项目现有实现。

**接管：做一个有限的小修改。** 例如补充某个错误分支的脱敏日志，或增加一个已有边界的回归测试。修改前先写预期，修改后解释为什么不会把“命令已接收”误判为“业务已完成”。

**完成证据：** 一张调用链图、一张资源表、一份测试结果，以及一个能由你解释每行意图的小 diff。

### 路线二 QUIC 传输与恢复状态

**入门：按责任画图。** 分开应用文件任务、项目 SDK、QUIC 库和操作系统网络。再分开“这笔传输是谁”“当前走哪条连接”“已确认收到多少数据”“接收端是否完成提交”。不要把自研 SDK 等同于自研 QUIC 协议栈，也不要把 SSH/SFTP 和自定义文件传输拼成同一条链路。

**基础：画两份状态表。** 分别列发送端与接收端的状态、触发事件、允许动作和错误出口。把“数据已发出”“接收端已落到临时文件”“校验通过”“最终文件已提交”“发送端收到完成确认”分成不同观察点。它们是否对应项目中的独立枚举，要回到源码判断。

**进阶：用假的网络与文件系统控制故障。** 至少推演三种时间线：传输中断；接收端已经完成但 ACK 丢失；旧连接的事件在新连接建立后才到。记录双方当时掌握的信息，再检查当前实现如何决定恢复、拒绝或重新开始。找不到处理分支就标记待验证，不把理想方案写成已有能力。

**接管：验证一个恢复不变量。** 例如“同一笔任务重试不能把另一个任务的临时文件当作自己的”或“没有完成确认时发送端不能显示已确认完成”。先说明项目实际采用的身份和确认语义，再设计测试。测试只操作临时目录和自有环境。

**完成证据：** 两端状态图、至少一条故障时序图、对应源码位置、实际测试记录或明确的未运行标记。仅看见重连成功，不足以证明断点数据正确或完成语义正确。

### 路线三 Agent 审批与真实执行边界

**入门：定位授权链。** 找到模型响应解析、工具参数准备、审批数据生成、用户选择、执行前检查和最终执行器。区分模型建议执行、界面显示批准和客户端实际允许执行。

**基础：记录审批绑定了什么。** 按源码逐项列出目标身份、连接信息、计划或参数、有效期等实际字段。没有的字段不补写成现有保护。再问“批准以后这些值可能改变吗”“执行时用的是审批快照还是当前全局状态”。

**进阶：替换为 fake executor。** 让执行器只记录调用次数、目标和参数，绝不运行真实远端命令。先批准目标 A，再把当前目标改为 B；再测试审批拒绝、取消、计划或参数变化，以及审批回调迟到。具体哪些变化应该使审批失效，需先依据产品语义写清契约。

**接管：检查复核和实际执行之间的空隙。** 如果复核后又读取可变全局目标，检查是否可能出现“检查 A，执行 B”。可控地在两步之间安排状态变化，证明执行器接收的是哪份上下文。补充测试不等于系统已经解决全部提示注入和远端状态变化风险。

**完成证据：** 授权链图、审批字段清单、fake executor 的断言结果。只验证出现错误提示不够，要验证被禁止的执行入口没有调用。

### 路线四 启动与 Flutter 页面生命周期

**入门：分清所有者。** 选一个实际页面，列出 AppRuntime 共享资源、页面 ViewModel、State、Timer、StreamSubscription 和 controller。记录谁创建、谁释放，页面退出是否应影响其他页面。

**基础：跟踪一个异步页面操作。** 发请求后立刻退出，再打开页面；控制旧请求最后完成。分别检查已销毁页面的更新、重复订阅和旧结果覆盖新结果。理解 `mounted` 检查只是防止一类无效 UI 操作，不自动取消网络任务，也不保证旧请求不会覆盖仍然挂载页面的新状态。

**进阶：控制初始化时序。** 让 fake initializer 暂停在中途，制造两次并发首次调用、初始化失败后重试、初始化中销毁。观察资源创建次数、共享结果、失败 Future 是否清理和迟到资源归属。是否允许销毁后重建，要按实际 owner 契约定义。

**接管：测量启动代价而非猜测。** 分别记录第一帧、首页可交互、首次功能 ready。保持设备、构建模式、数据和缓存条件一致；多次重复并保存原始结果。把初始化移到首次点击可能转移等待，不是无成本消除等待。新补测只能支持所测版本和条件，不能自动证明旧简历中的历史提升。

**完成证据：** 资源所有权图、初始化与页面竞态测试、带环境信息的测量表或“尚未测量”。切后台、路由退出、系统杀进程应分开讨论；不能假设系统杀进程前一定完成 Dart `dispose` 清理。

## 三 Fake 测试的明确验收标准

Fake 是可控制行为的替身，例如“先不返回，等测试发信号再完成”的初始化器。它用于稳定重现时序，不能单独证明真实 FFI 内存安全、真实网络兼容性或真机性能。单元测试通过后，还需按风险补集成和真机验证。

优先使用可控时钟、Completer、闸门或显式事件驱动，避免依赖“睡 100 毫秒应该就好了”。预期先写在测试之外，再读实现，减少测试和 AI 代码共享同一错误假设。

### 初始化

| 场景 | 可控输入 | 应验证的行为 |
| --- | --- | --- |
| 并发首次请求 | 第一次尚未完成时再调用一次 | 底层创建次数为 1；两调用者得到同一资源或同一次结果 |
| 首次失败再请求 | 第一次返回错误，第二次成功 | 第二次确实重新尝试，不永久复用失败结果 |
| 初始化中销毁 | 暂停创建，销毁 owner，再完成创建 | 不向已销毁 owner 发布资源；迟到资源按约定关闭且不重复关闭 |
| 销毁后再次请求 | 已进入终态后调用 | 按契约明确拒绝，或由新 owner 重新创建；不能悄悄复活旧实例 |

### Pending 请求

| 场景 | 可控输入 | 应验证的行为 |
| --- | --- | --- |
| 正常结果 | 对应 ID 返回一次 | 只完成一次；移除 pending；清理关联计时器 |
| 入队失败 | fake transport 拒绝请求 | 调用者收到明确失败，不残留 pending 或计时器 |
| 超时后迟到 | 推进时钟触发超时，再返回事件 | 保持原终态，不再次完成或更新已结束请求 |
| 重复事件 | 同一 ID 返回两次 | 第二次不重复完成，不破坏其他请求 |
| Dispose 时未完成 | 保留多个 pending，再销毁 | 全部按契约结束并清理；后续事件不能复活请求 |
| 新旧会话交错 | 新会话开始后返回旧事件 | 旧结果不能误匹配新请求；检查 ID 唯一性或会话隔离措施 |

### 审批

| 场景 | 可控输入 | 应验证的行为 |
| --- | --- | --- |
| 用户拒绝 | 明确拒绝审批 | 危险执行器调用次数为 0 |
| 批准后切换目标 | 批准 A，然后改成 B | 不因当前目标变化而在 B 上执行；按契约拒绝或要求重新审批 |
| 批准后修改计划 | 修改授权范围内的关键字段 | 旧审批不被当成对新操作的授权 |
| 取消后回调 | 取消任务后才返回批准事件 | 不恢复已取消任务的执行 |
| 复核后目标变化 | 在复核与执行之间改变全局状态 | 执行上下文不被偷换；拒绝或使用已绑定的合法快照 |

测试使用假的无副作用执行器。哪些操作属于危险操作、哪些字段是授权关键字段，应按真实契约定义，不能简单把所有对象变化都视为审批失效。

### Flutter 生命周期

| 场景 | 可控输入 | 应验证的行为 |
| --- | --- | --- |
| 页面退出后 Future 完成 | 退出页面，再完成 fake 请求 | 不更新已销毁页面；资源按 owner 规则处理 |
| 请求先后顺序倒置 | 新请求先完成，旧请求后完成 | 若业务要求最新请求优先，旧结果不能覆盖新状态 |
| 多次进出页面 | 重复创建与销毁页面 | 订阅与 Timer 不累积；每次事件不重复处理 |
| 页面借用共享服务 | 关闭单个页面 | 不销毁仍供其他页面使用的应用级资源 |
| 状态通知与内部任务 | 页面取消订阅但任务仍运行 | 测试明确区分不再展示、停止等待和底层取消，不把它们混成一个断言 |

以下仅为教学测试伪代码，不是仓库 API 或现有测试：

```text
executor = FakeExecutor(recordOnly = true)
approval = approve(target = A, operation = X)
currentTarget = B
result = runUsingApproval(approval, executor)
assert result rejects_or_requires_new_approval
assert executor.calls.count == 0
```

如果真实产品选择“继续针对已批准的 A 执行”，应先确认该契约并相应更改预期；无论如何不能用批准 A 的授权执行 B。不要为了让测试通过而改变授权含义。

## 五 评审 AI 代码时要问的十个问题

1. **需求是否被悄悄扩大了？** 本来只需修错误提示，却生成了新状态层、缓存或依赖，有没有必要？
2. **依据在哪？** API 和方法签名是否真存在于项目锁定版本，还是 AI 根据其他版本猜测？
3. **成功到底代表什么？** 入队、写入缓冲、对端接收和业务完成有没有混淆？
4. **资源谁负责？** 正常、失败、取消、超时和销毁路径是否都能说明所有者与清理？
5. **状态在哪些时刻会改变？** 每个异步暂停点之后，目标、页面、会话和任务是否仍然有效？
6. **输入能否被信任？** 服务器输出、模型参数和文件名能否绕过校验、审批或边界？
7. **失败是否被吞掉？** 大范围 catch、空错误处理、无上限重试是否掩盖真实失败？
8. **测试能推翻它吗？** 有没有至少一个“实现错误时必须失败”的反例，而不只是正常路径？
9. **有没有更简单的方案？** 增加队列、线程、Isolate 或缓存的收益和生命周期成本分别是什么？
10. **结论是否超出证据？** 测试通过、代码分块、删掉定时器都不能自动推出生产可靠、固定峰值内存或明确提速比例。

面试官可能继续问“AI 给过你什么错误建议”。若没有真实记录，就说还没有整理出可复核实例；不要把以上风险任选一个包装成亲身经历。之后遇到实际问题再保存原建议、你的判断、验证和最终修改。

## 六 准备完成的标准

不用以“读完多少页”验收，用下面五项检查：

- [ ] 我能明确说出两个最熟悉的模块，以及不熟悉的模块。
- [ ] 我能不看手册画出一条真实调用链，并在源码中找到对应位置。
- [ ] 我能解释至少一个失败时序，而不仅是正常流程。
- [ ] 我有一份自己做过的小修改或测试记录，能区分 AI 生成与本人验证。
- [ ] 我能说明测到什么、没测什么，并主动收窄过度的简历表述。

如果时间紧，先做 SDK pending 路线和页面生命周期路线；它们更容易在有限环境中验证，也能直接体现 Android 实习岗位重视的异步、状态、资源和排障能力。QUIC 与 Agent 保持清楚的责任边界，再逐步深入。
